## 四、本轮问题明细

### P1-1｜Creo 10 SDK 整包编译阻断：`Probbl.h` 硬包含未做源码级门控

**现象（可复现）**

```
$ .venv/Scripts/python.exe bridge.py build
Native build failed (2)
Build error summary (last 15 error lines):
native\surface_loft.cpp(15): fatal error C1083: 无法打开包括文件: "Probbl.h": No such file or directory
```

```
$ ls "D:/Program Files/PTC/Creo 10.0.0.0/Common Files/protoolkit/includes/Probbl.h"
No such file or directory
```

**机制**

1. `tools/generate_constants.py` 的 BUG-107 门控是**对的**：`available_headers()` 把缺失头从 `HEADERS` 剔除，既不扫枚举也不产出 `#include`，并打印 `MISSING_SDK_HEADER=Probbl.h`。本机 `native/constants.inc` 确实不含 `Probbl.h`。
2. 但 `native/surface_loft.cpp:15` 是**手写**的 `#include <Probbl.h>`，不经过生成器；`generic.cpp:3886` 又无条件 `#include "surface_loft.cpp"`。
3. 于是门控对生成器有效、对手写 TU 无效；`Probbl.h` 一缺，整个编译单元在预处理阶段就 fatal，**任何 feature 都编不出来**，不是「surface_loft 不可用」而是「整个 MCP 不可构建」。

**为什么算问题**

- 本项目从 BUG-107 起确立的原则是「按存在性门控，缺失头不进入编译单元」，`docs/COMPATIBILITY.md` 也把 Creo 9/10 列为支持/要求范围。
- 作者已在 0.18.3/0.18.4 的「未测范围」声明「Creo 9/10 未复测」，这解释了**行为**未验证，但不能解释**构建**直接失败：声明支持的平台上连 worker 都生成不了，等价于该版本在 Creo 10 上不可安装。
- 契约测试 `tests/unit/test_gated_headers.py` 4 项全绿，恰恰暴露门控覆盖面不足：它只断言「生成的 constants.inc 只 include 存在的头」，没有任何用例检查**手写 `native/*.cpp` 里的 `#include <X.h>` 是否也受门控**。这正是「规范/门控新增 ≠ 覆盖到位」的又一次实例（0.11.1 是生成器漏门控，这次是手写 TU 漏门控）。

**建议（按成本从低到高）**

1. `surface_loft.cpp` 改为 `#if __has_include(<Probbl.h>)` 门控，缺失时提供与其它 gated 算子一致的「不可用」失败回执（本机补丁即此形态）。
2. 更彻底：让 `generate_constants.py` 对 `HEADERS` 中每个缺失项额外产出 `#define MECHDOG_HAS_<SANITIZED_HEADER> 0/1`，手写 TU 统一用该宏把**所有** SDK 版本相关头纳入同一门控体系（与 `MECHDOG_HAS_ProSmt*` 的既有做法对齐）。
3. 把契约测试扩到源码层：解析 `native/*.cpp|*.h` 的 `#include <X.h>`，断言每个 `X.h` 要么在 `HEADERS` 内、要么被 `MECHDOG_HAS_*`/`__has_include` 包裹。
