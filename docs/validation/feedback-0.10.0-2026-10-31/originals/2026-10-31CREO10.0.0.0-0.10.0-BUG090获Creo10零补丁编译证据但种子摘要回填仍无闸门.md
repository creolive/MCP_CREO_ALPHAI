## 1. 好消息（本轮最重要）：BUG-090 的 Creo 10 定向编译，本机一次通过，且**零本地补丁**

BUG-090 卡里写着"离线修复已交付（0.10.0，N01 函数门控+统一实读回退，本机 Creo 12.4 编译通过），**Creo 10 定向编译与实机待复验**"。本机正好补上这一项：

**① 编译结果**

```
pip install --no-deps -e .   → Successfully installed MCP_CREO_MechDog-0.10.0
bridge.py build              → 成功（未套任何本地补丁；此前的本地 #ifdef 补丁已被上游代码取代）
creo_worker.exe              → 9,510,912 → 9,581,568 B；指纹 5ea407be…
```

**② 探针行为正确（这是关键，值得记进 BUG-090 证据）**

本机 `bridge.py build` 自动重生成的 `native/constants.inc`：

```
#define MECHDOG_HAS_ProSmtPartThicknessGet      1     ← Creo 10 有此 API（尺寸回退可用）
（无 MECHDOG_HAS_ProSmtPartThicknessValueGet）          ← Creo 10 无此 API（门控关闭）
```

即：`FUNCTION_PROBES` 的两项探测各自独立生效，**Creo 10 恰好只关掉缺的那一个**，回退链自然落到"厚度尺寸读取"。

**③ 语义比我上轮的本地补丁更好**

我上轮的做法是"读不到就把板厚当未知 → 字段 null"。上游改成了单一 `part_thickness_read()` 的三级回退（值接口 → `ProSmtPartThicknessGet` + `ProDimensionValueGet` → `SMT_THICKNESS` 参数），并且注释明确了边界：

> Without the value getter the fallbacks read the same model state through the thickness dimension or the `SMT_THICKNESS` parameter that drives it (BUG-032/T03), so the value still comes from the model and never from the request. When no path can read a value the caller must treat the thickness as unknown…

**结果是：Creo 10 上板厚仍然是真实读数，不是 null** —— 这比我提的降级方案更完整。我的本地补丁已删除，后续升级不再需要任何本地修改。

**④ 附带机制（防复发做得比我建议的更全）**

`tools/test_sheetmetal_contract.py` 新增 `GATED_SDK_CALLS = ("ProSmtPartThicknessGet", "ProSmtPartThicknessValueGet")` 与 `unguarded_sdk_calls()` 断言：**门控 API 只能出现在匹配 `MECHDOG_HAS_<name>` 的 `#ifdef` 正分支内**，且注释文本不算调用。这条静态契约能直接挡住"下次又裸调一个只在 12.4 存在的 API"。

**建议**：把上面的 ① ② 登记为 BUG-090 的一条外部证据（环境：Creo 10.0.0.0 / VS2022 14.44 / Python 3.13，日期 2026-10-31），状态可细化为"**编译已在 Creo 10 外部环境通过；仅实机建模待验**"。仍不建议直接填"已修复"——实机确实未验，现在的写法是对的。

## 2. 核心问题（新）：种子摘要回填仍是**无闸门的手工步骤** —— 0.10.0 修了值，没修类

0.10.0 的"升级必读"里，作者把这条写得非常坦诚：

> 种子包校验摘要随版回填（修复 0.9.0 遗留缺陷）：0.9.0 未把种子包 SHA256 回填进 `seeds.py` 的 `expected_digest`（仍指向 0.8.5 包），导致其已发布源码包安装时拒绝配套种子包。

**值确实修好了**（实测）：`seeds.py` 期望 `99e3b9ec92593fbd…` = 0.10.0 种子包实际 SHA256；两份 manifest 均为 0.10.0；9/9 种子哈希通过。

**但我复查了三个可能做成闸门的位置，全部保持原样**：

| 位置 | 现状 |
| --- | --- |
| `tools/package_seeds.py:53` | 仍只有一句打印：`"For a new release, set seeds.py expected_digest to this archive SHA256 before packaging source."` —— **它已经算出这个哈希，却不写回、也不校验** |
| `docs/development/RELEASING.md` | 检查单（3/4/6 步）仍无"回填 `seeds.py` 摘要"这一项 |
| `tests/` / `tools/test_*.py` | 仍无任何用例走 `install_seed_library(archive_file=...)`；`grep archive_file` 只命中一个无关用例 |

**为什么这条一定会再犯**：种子包内嵌 `compatible_server_version`，**每发一版都要重新打包、哈希必变** → `expected_digest` 每次都得手改。0.8.1 犯过一次（清单版本），0.9.0 犯过一次（摘要），两次都是"人忘了"。按现在的结构，第三次只是时间问题。

**建议（任选其一，成本都很低）**：

1. **首选**：`package_seeds.py` 生成归档后**直接回写** `seeds.py` 的 `expected_digest`（哈希在内存里已有），或在 `--output` 后加断言：`sha256(archive) != seeds.py 期望值 → exit 1`；
2. 加进 `RELEASING.md` 的单号检查项（与"README 版本段"并列——那条也是因为 0.3.6 遗漏才立起来的）；
3. **补一条测试**：`install_seed_library(archive_file=<刚构建的种子包>)` 必须成功、篡改一字节必须拒绝。这条测试能同时挡住 BUG-089 和本次复发，而且完全离线。

## 3. 核心问题（新，影响自动化重放）：盲孔 `depth` 改为钻尖口径，却**没有机器可读的口径标记**

变更本身是对的（`PRO_HLE_DEP_SHOULDER_DIM_SCHEME` → `PRO_HLE_DEP_TIP_DIM_SCHEME`，对齐冻结契约的 overall 语义），披露也做到了教科书级：版本说明把"旧总深 = depth + 钻尖高（118° 约 0.3×基本径）""同输入重放会得到更浅的孔""既有模型不被改动"都写清了，N10 六例实机数值也给了。

**问题在于：这些信息只存在于"版本说明"里，不在"响应"里。**

- 我在 `src/`、`server.py`、`native/*.cpp` 全库搜 `depth_basis` / `tip_depth` / `钻尖`：**零命中**；
- 也就是说，一个按存储的 JSON 计划重放的自动化客户端，在 0.9.0 与 0.10.0 上提交**同一份 hole 请求**，会得到体积不同、深度不同的孔，而**响应里没有任何字段能说明"这次用的是哪种口径"**。

这和 BUG-080（装配变换声明毫米、实为原单位）是同一类问题：**契约变了，但调用方无法从返回里察觉**。BUG-080 的修复给出了正确范式——除修数值外，还加了 `length_unit`（单位名+系数+查询码）与 `transform_to_parent_raw`，让调用方能自证。

**建议**：在 hole 结果（或 `operation_results`）里加一个稳定字段，例如

```json
{"depth_basis": "tip", "depth_scheme_query": "PRO_HLE_DEP_TIP_DIM_SCHEME"}
```

并在 README 的接口表 hole 行注明"0.10.0 起 custom 盲孔为钻尖口径"（目前该行只写"沉孔/沉头 T12 指定 3/3 实机通过"）。有了这个字段，重放工具就能在跨版本时自动识别口径、必要时拒绝或换算，而不是拿到一个"看起来成功但浅了 0.3×基本径"的孔。
