## 1. 核心问题 A（P1）：Creo 10 编译阻断跨 0.8.0→0.9.0 六版未修，且 0.9.0 把它用进了核心建模路径

### 严重性变化（相比我前两份报告）

| 版本 | `ProSmtPartThicknessValueGet` 的用法 | 对 Creo 10 的后果 |
| --- | --- | --- |
| 0.8.0–0.8.5 | 1 处，法兰壁 relief 的**信息性字段**（厚度未知→null） | 编译失败；补丁后功能可用 |
| **0.9.0** | **3 处**：`sheetmetal_wall` 同步前读取（读不到即 `throw`）、同步后复读（读不到即 `throw`）、法兰 relief 记录 | 编译失败；补丁后 `sheetmetal_wall` 的"板厚同步已生效"这一**证明环节无法执行** |

0.9.0 的两处新增调用写在 BUG-032 的修复里，语义是"**读不到就不许假装同步成功**"——方向正确，但对没有该 API 的 SDK 来说，等于把整条 `sheetmetal_wall` 变成编译期不可用。

### 复核结果（0.9.0 包内）

- `native/advanced.cpp`：第 375、421、612 行三处调用，**全部无 `#ifdef` 守卫**；
- `tools/generate_constants.py`：`PROBES` 仍是 2 个**常量**（`PRO_E_HLE_ADD_PARAMETERS`、`PRO_HOLE_NO_PARAMETERS_FLAG`），未加函数声明探测；
- 我对 0.9.0 **全部**原生文件做了 Pro\* 声明扫描（对 Creo 10 SDK 头文件全文）：缺失的仍**只有这一个** API（`ProSmtPartThicknessGet` 在 Creo 10 是存在的）；
- 发布说明仍写"Creo 10 未复测"，未体现"编译不通过"。

### 报告接收情况

`docs/validation/` 下最新反馈归档仍是 `feedback-0.7.2-2026-10-28`。我 10-29 的 **0.8.2 报告**与 10-30 的 **0.8.5 报告**均未归档。对照历史：0.4.1/0.4.2 时期曾有 `feedback-0.4.1-creo10-build-2026-10-20`、`feedback-0.4.2-creo10-2026-10-21` **专属的 Creo 10 构建反馈目录**——说明这条通道本来就存在，只是最近两份没进去。

### 建议（沿用上次方案，补上 0.9.0 的新情形）

**① 机制：把 BUG-033 的编译探测从"常量"扩展到"函数声明"**

```python
# tools/generate_constants.py
FUNCTION_PROBES = ("ProSmtPartThicknessValueGet",)   # 命中即写 MECHDOG_HAS_ProSmtPartThicknessValueGet 1
```

**② 代码：三处调用按语义分别降级**（关键是别把"没法证明"写成"证明通过"）

- 第 612 行（法兰记录）：`thickness_known=false` → 字段 null（代码原本就支持）；
- 第 375/421 行（板厚同步证明）：无该 API 时**仍执行** `SMT_THICKNESS` 参数写入与体积复核（这两步不依赖它），但把 `part_thickness_before_mm` / `part_thickness_mm` 输出为 **null**，并新增一个显式标记（如 `part_thickness_readback_available=false`）。这样 Creo 10 用户能建模、能看体积证据，也**不会误以为板厚已被证明同步**。

我的本机补丁就是按 ② 做的（见 §5），可直接参考。如果你更希望"Creo 10 上明确拒绝 `sheetmetal_wall`"，那也应给一个稳定的拒绝码（例如 `SHEETMETAL_THICKNESS_READBACK_UNSUPPORTED`）而不是编译失败——**编译失败连能力边界都表达不出来**。

**③ 文档**：发布说明把"Creo 10 未复测"改为可判定表述，或加一节"SDK 门控 API 清单（最低 SDK 版本）"。

## 2. 核心问题 B（P1）：0.9.0 的种子包会被它自己的 `creo_install_seed_library` 拒绝（BUG-089 同类复发）

### 实测（纯哈希比对，无写入）

```
0.9.0 种子包 SHA256 : 5933e0adeb250f2a80b74e6e...
seeds.py 期望值      : 4178f8aaa0509653915a8238...   ← 这是 0.8.5 的种子包哈希
=> 判定：拒绝（seeds.py:163-164 直接比对 ZIP 字节）
```

即：**随 0.9.0 发布的种子包，用文档给出的安装接口装不上**；而 README 第 9 行又写着"升级请使用 **0.8.5** 种子包"——两条一起看，等于承认了这次漏更。

### 为什么又漏了（这是本轮最值得改的地方）

不是粗心，是**这个步骤一直是手工的**：

1. `tools/package_seeds.py` 第 53 行只打印一句提示：`"For a new release, set seeds.py expected_digest to this archive SHA256 before packaging source."` —— **提示，不是闸门**；
2. `docs/development/RELEASING.md` 第 5 步只要求"检查种子及 SHA256"，**没有"回填 `seeds.py` 摘要"这一条**；
3. BUG-089 的验收范围里写了"回填 `seeds.py` 摘要并再构建核对"——0.8.2 那次是**手工做对的**，没有留下机制；
4. `tests/test_portable_modeling.py` 只调用 `install_seed_library()`（**目录模式**），从不传 `archive_file`，所以 archive 摘要校验这条路径**没有回归测试**；1343 项测试全绿也发现不了。

### 建议

- **首选**：让 `package_seeds.py` **自动回写** `seeds.py` 的 `expected_digest`（它已经算出了这个哈希，只是打印而不是写回）；或反过来，让 `seeds.py` 从 `seed_package.json`/常量表读取，杜绝两处手抄；
- 若坚持手工：把它写成 `RELEASING.md` 的**编号检查项**，且发布脚本在打包源码前做一次断言（`sha256(种子包) == seeds.py` 否则 exit 1）；
- **补一条单测**：用真实种子包走 `install_seed_library(archive_file=...)`，断言通过；用篡改字节的包断言拒绝。这条测试会直接挡住 BUG-089 及其复发。

## 3. 相关：README 的"当前正式版"段没更新（同类第二次）

0.9.0 包内 README **全文没有出现 `0.9.0`**，第 9 行仍写"当前正式版 **0.8.5**"。而 `docs/development/RELEASING.md` 第 20 行明确写着：

> **发版清单必须包含 README 标题与版本段**（0.3.6 曾遗漏，以 0.3.7 勘误补救）。

也就是说这条检查项**已经因为同类遗漏立过一次**。建议把"README 版本段 / 种子 digest / 两份种子清单版本"合并为发布前的一条 `--check-release` 自动校验（一次性断言 version.py、README、两份 manifest、seeds.py 四处一致），比在文档里加提醒更可靠。

## 4. 已闭环与正面（据实）

- **BUG-032 板厚语义修复落地**：0.9.0 改为写 `SMT_THICKNESS` 参数再再生、复验体积与回读，1 mm 壁的零件板厚从 3.71 → **1.0**，五组矩阵体积误差 0.0，`saved_file_reloaded_and_verified=true`。这正对应我 0.8.5 报告里引用的"3.71 不可信"，闭环得干净。
- **我 0.8.5 报告 §2 的建议已被采纳（以更严谨的方式）**：作者没有新开卡，而是给 BUG-085 补了 2026-10-30 离线调查——**两套完整时间线**（0.6.1 断连 vs 10-29 挂起）、worker 构建身份/进程/nmsd/IPC/锁证据表、矛盾点 6 项与缺证清单，并给出关键判据：`-4`/exit 20 在"无 Creo 进程"场景同样出现，**同码不构成同根**；明确"不重开 BUG-056"。这比单开一张空卡更有价值，我认可这个处理。
- **T13 `native_bundle` 从"不通过"转为导出 `complete=true`**，同会话回导被 `SESSION_NAME_CONFLICT` 拒绝这一条也讲清了原因（受管模型不可擦 + 装配检索要求空会话），并给出隔离会话回导通过（组件 2/2、位姿一致）。
- **能力边界定因写得实**：折边附着边端部与既有折弯相邻必然失败并回滚、四壁不支持、corner relief 未实现——把"不支持"从现象升级成可判定的规则。
- 发布证据链稳定：种子包三次构建同哈希、源码包两次一致、1048 文件、禁入路径 0。
