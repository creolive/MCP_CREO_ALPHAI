# 2026-11-01 CREO MCP_CREO_MechDog 0.11.0 反馈：受管装配上色解锁链路三处断裂与装配失败恢复死路

- 测试对象：MCP_CREO_MechDog **0.11.0**（FEAT-052 recolor_assembly 首次实测）
- 环境：Windows 11 x64 / Creo Parametric 10.0.0.0（release_numeric=42）/ 80 组件 Strandbeest 受管装配（12 零件族）
- 测试性质：0.11.0 新功能验收（`creo_recolor_assembly`），从 0.10.0 时代遗留的受管检查点出发走完整解锁链

## 〇、执行结果摘要（先说结论：功能本身质量很好）

最终上色**成功**：`painted=80/80、unmatched=0`，12 族自动分组计数正确（12/6/6/12/6/2/1/18/6/1/4/6），写后读回 80/80 与保存重载读回 80/80 全部在 1e-6 容差内，外观随 `.asm.6` 持久化，revision 4→5。dry-run 的分组预览、逐族计数、基线缺失清单（missing_count + missing_labels）都准确好用。

但达成这一步之前，解锁链路断了三次，其中一次只能靠**手工编辑注册表**才能继续。以下按阻断顺序列出。

---

## 核心问题 1：旧检查点升级到 0.11.0 后，recolor 无自动迁移（升级摩擦）

**现象**：0.10.0 时代保存的受管装配检查点，其组件快照没有 `appearance` 字段（FEAT-052 新增）。`creo_recolor_assembly` 的 dry-run 如实报告了基线缺失（`present:false, missing_count:80`），执行被拒，提示"run creo_save_model on the assembly to establish and verify a new checkpoint"。

**影响**：升级到 0.11.0 后，**所有** 0.10.0 之前创建的受管装配都需要手动补一次 save 才能上色。单个模型还好，装配多的项目会逐个撞到。

**建议**：三个方向任选——
1. dry-run 检测到基线缺失时，在回执里直接给出"一键补基线"的作业（例如 `refresh_baseline:true` 参数触发一次仅重存检查点的轻量作业），省去用户手工拼 save 调用；
2. 或在 release notes / 工具描述里显式声明"0.10.x 检查点需先 save 一次"；
3. 或 recolor 执行路径遇到旧检查点时自动降级为"先 save 再 recolor"的一次性作业（保持原子性）。

---

## 核心问题 2：同名会话残留阻塞 save，错误信息不含解锁路径（链路断裂 ×2）

**现象**：会话里存在同名装配 `STRANDBEEST_ASM`，但其 origin 是外部目录（`...\CREO_build\asm_components\strandbeest_asm.asm.8`，由外部程序保存）。此时：

- `creo_save_model` 失败：`Loaded model origin does not match this MCP model's output directory`——**没有提示"应先擦除会话副本"**；
- 转向 `creo_erase_session_models`，又被 `modified` 标志挡住：`The model has unsaved changes; save or discard them in Creo first`——**没有说明保存之后还要回到 erase**；
- 用户必须在 Creo GUI 手动保存（清脏位）→ erase → save，三步全靠自行排查拼出。

**复现**：任何"会话里有非受管来源的同名模型"场景（外部程序、GUI 手动打开、上次会话残留）都会命中。

**建议**：
1. `save` 的 origin 不匹配错误里，检测到会话存在同名模型且非本 MCP 来源时，直接附加引导："session has a same-name model from <origin>; erase it via creo_erase_session_models (targets=[{name, model_type}]) then retry"；
2. `erase` 的 modified 拒绝信息同理，附加完整链路："save in Creo GUI to clear the dirty flag, then re-inspect and apply erase"；
3. 进一步：考虑给 `creo_save_model` 增加 `adopt_session_copy:true` 之类的显式参数——当会话同名模型与受管检查点组件结构一致时，允许用户声明"以会话副本为准"走一次受管保存，避免 erase→reload 的来回。

---

## 核心问题 3：装配的失败 save 造成恢复死路，只能手工编辑注册表（最严重）

**现象**：核心问题 2 里那次失败的 save（发生在 connect 阶段，**零变更**、未触任何模型）把受管模型的 `status` 置为 `failed`。此后：

- `creo_save_model` / `creo_recolor_assembly` 一律拒绝：`Model is not ready; inspect its last job before recovery`；
- 按提示走 `creo_reconcile_model(mode=inspect)`，返回的四个恢复动作（`restore_baseline / accept_saved / accept_live / abandon_new`）**全部不可用**，原因均为 `Assembly/drawing reconciliation is not supported; preserve component ownership`；
- 结果：**没有任何官方工具能把装配从这次零变更失败中恢复为 ready**。唯一出路是手工编辑 `models/<id>/model.json` 把 `status` 改回 `ready`（本次实测有效，因为该失败确实零变更）。

**影响**：装配模型一旦出现任何作业失败（哪怕是无害的预检拒绝），就进入"官方工具不可恢复"状态。这不是理论风险——本次是第一次 save 就命中了。

**建议**：
1. 区分失败性质：connect/预检阶段（native 未启动或零变更）的失败不应把 status 置为 `failed`，或至少应置为可自动复位的中间态（如 `failed_no_mutation`）；
2. 为 assembly 提供最小恢复动作：哪怕不支持完整的 reconcile 语义，也应有 `ack_failure`（确认零变更后复位 ready）这类显式操作，替代"手改 model.json"；
3. 短期文档补救：在 `creo_reconcile_model` 的描述里写明"assembly 不支持恢复动作；零变更失败可编辑 model.json 的 status 字段"——目前这一出路完全没有文档记载。

**附带观察**：`model.json` 的 `status` 字段可被外部直接编辑且注册表照常接受（本次正因此解锁）。这既说明注册表无完整性校验，也恰好证明"提供一个官方等价操作"是低成本高收益的。

---

## 次要问题与体验建议

1. **自动分组的 palette 键是 source_model_id（UUID）**：想用自动分组上色，必须先 dry_run 拿到 12 个 UUID，再手拼 palette 二次调用。建议：palette 键同时接受零件名（如 `p10_ebd_tri2`）或提供 `random:true`（自动分组 + 随机鲜色）一步到位——本次"随机上色"需求实际花了三步（dry_run → 本地生成调色板 → 执行）。
2. **preview 的 `view_matrix_matches:false`**：保存/重载后预览视角与当前视角不一致，回执里是提示性的，不影响功能，但每次都出现在结果里，建议在文档里说明其含义或达标条件。
3. **erase 的 inspect 回执体量**：单目标擦除时 `remaining_after` 仍列出全部 80 个组件（约 3 页输出）。建议 compact 模式只回 counts + 抽样。

---

## 确认变好 / 值得保留的设计（正向反馈）

- **dry-run 完全离线**：只读注册表，不锁通道、不建作业、不动 revision，分组/计数/基线缺失一目了然——这次解锁排障全靠它；
- **双重读回**：写后读回 + 保存重载后读回，1e-6 容差全部通过，外观持久化有证据链；
- **基线三态记录**（present/absent/query_failed）：80 组件的 baseline 都带原始 query_code，不造假；
- **erase 的证据链设计**：inspect → evidence_token → apply，逐项重验 origin/modified，擦除后双查询确认缺失——本次用它清会话副本一次通过；
- **外观写在装配组件层**：源零件文件字节不动，符合逆向交付"不污染零件"的要求。
