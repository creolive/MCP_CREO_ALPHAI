**事实**

| [DEV-075](../work-items/DEV-075.md) | 开发中 / 0.18.2 | 开发中（离线实现，未连接 Creo）/ 0.18.2
  | t07 provenance 无 git 降级、附件 asset API 二级通道、发布规范与逐 ID/POSTCHECK 回填、FEAT-059 措辞

而 0.18.2 已是正式 Release（`prerelease = false`，`published_at 2026-11-07T10:18:16Z`），`RELEASING.md:18`、`RELEASE-0.18.2.md`、`RELEASE_NOTES_0.18.2.md`、Release body 均以完成口径描述本版；`RELEASE-POSTCHECK-2026-11-07.md` 与 `DEV-075.md` 自身也是「发布后复核」的产物。

**为什么算问题**

1. `RELEASING.md:39` 第 8 步明文要求「`version.py`、当前版本说明、`DEVELOPMENT.md`、本文件『当前版本为 X』行、主台账（含完成档案）、**本版交付 ID 的工作卡首页**及远端 GitHub Release 必须一致」，且「不允许旧版本遗留的『未发布』描述继续出现在当前入口、主台账或版本说明首部」。`DEV-075` 是 0.18.2 唯一的交付 ID，其卡首页正是核对对象。
2. 同一张逐 ID 表内，「开发中 / 0.18.2」与「**无**（本卡离线项全部关闭）」「**一致**」不能同时成立：若全部关闭且判一致，状态不应是开发中。
3. 同批已有现成的正确写法，说明这不是「实机未验证所以必须保留开发中」的策略选择：
   - `DEV-072.md:3`：`状态：已交付 0.17.4（离线代码 + 原生组合编译；Creo 实机未执行）。目标版本：0.17.4（已发布）。`

   即「已交付/已完成 + 括号内保留实机未验 caveat」即可完整表达，无需把状态留在开发中。
4. 与 0.18.0 反馈中的 `FEAT-057` 卡「已发布仍开发中」属同类。作者在 0.18.1 专门修了 `FEAT-057` 并把第 8 步规则写得更严，本版自身的工程卡却漏了回填，属于「规则覆盖对象扩写后未回头核对自己」。

**建议**：把 `DEV-075.md:3` 改为 `状态：已交付 0.18.2（离线门禁与源码包解压单测；Creo 实机未执行）。目标版本：0.18.2（已发布）。`（措辞照 `DEV-072`），并同步 `RELEASING.md:50` 的两列状态；若确需保留开放项，应把「无（本卡离线项全部关闭）」改为具体开放范围，并把结论列从「一致」改为「不一致/待回填」。另外建议把「本版交付 ID 的工作卡首页」核对从 FEAT 显式扩到 DEV/工程卡，避免只查能力卡。
