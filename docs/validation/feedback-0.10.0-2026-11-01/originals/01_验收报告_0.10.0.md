## A【核心，未修复】coordinates 模式对 0.0017 mm 求解位移仍整轮廓拒绝

**输入**：与 0.9.0 验收完全相同的 6 图元闭合轮廓（3 段 R25 圆弧 + 3 条直线，端点共用到 1e-9），`dimensioning="coordinates"`，模型 `v10_a_profile`：

```
message: "Coordinate dimensioning changed the supplied geometry; maximum deviation mm=0.001662"
failed_stage: execute_sketch
```

native log 的 `COORDINATE_DEVIATION` 六行与 0.9.0 **逐位相同**（`l1 point=end axis=1 moved=0.001658875502`、`l2 point=start axis=0 moved=0.001662400080`…）。也就是说，发布说明里的 BUG-049/N03（“端点诊断 `max_endpoint_gap_mm`”）只是把**诊断**做出来了，**行为本身**（超 1e-4 的求解位移 → 整体拒绝、无任何放行选项）没有变化。

一个值得注意的反证：失败回包里新增的

```
"max_endpoint_gap_mm": 4.90405093018823e-10
```

说明调用方输入的轮廓**闭合质量是 5e-10 mm**，远优于 `closure_tolerance_mm: 0.0001`。轮廓本身没有任何“散口”问题——被拒的唯一原因仍是坐标求解器的重排位移。诊断字段变好了，判定逻辑没变。

**建议（与上轮相同，重申）**：
1. 把闸值做成参数（如 `coordinate_tolerance_mm`，默认 1e-4）；
2. 或提供 `dimensioning="coordinates_lenient"`：位移 ≤1e-3 放行并回显 deviation；
3. 根因修复：重合点只加一次坐标约束（对“弧端点=线端点”重复成对加坐标尺寸是超定来源）。

## D【核心，仍未修】autodim 静默改几何，0.10.0 依旧无 deviation 告警

同一轮廓改 `autodim`（模型 `v10_b_autodim`）成功提交，但：

| 指标 | 0.9.0 | 0.10.0 | 正确值（尖角三解 + R25 圆角） |
|---|---|---|---|
| 板截面积 | 136495.031 → 成形面积未核对 | **成形面积 135264.98**（= 4057949.4757/30） | 136486.4 |
| 面积偏差 | −0.90 %（实测半径变 26.1） | **−0.90 %** | — |
| 回包告警 | 无 | **仍无** | — |

0.10.0 的 autodim 结果与 0.9.0 同源失真（面积仍偏小 0.90 %），而 `sketch` 成功回包里新增的 `native_section.max_endpoint_gap_mm: 0.0`、`max_cluster_spread_mm: 8.88e-15` 反而给读者“截面完美”的印象——**这些端点诊断衡量的是输入轮廓的闭合质量，不是求解位移**。发布说明为 FEAT-051 给 round/chamfer/draft 加了 `volume_before/after/delta` 可观测性，但 `sketch` 的 autodim 求解位移依然不可观测。

**建议**：给 `sketch` 结果加一个与 FEAT-051 同级的字段：autodim 求解后逐实体 `deviation_mm`（或至少 `max_deviation_mm`），超过 1e-3 置 `geometry_modified: true` 并在 `message` 里给出警告。这个数据在 `SectionRegenerate` 之后的 `ProSectionEntityGet` 里已经有了（coordinates 模式的 `COORDINATE_DEVIATION` 日志证明代码路径存在），只是 autodim 没有做比对。

## E【未修复】失败作业仍占用模型名，无释放路径

`v10_a_profile` 因 A 失败后，同计划（仅 `dimensioning` 改为 autodim）用同名重交，失败点提前到 connect：

```
message: "New model name already exists in the Creo session"
failed_stage: connect
```

与 0.9.0 行为一致。失败作业没有 prt 落盘，但会话对象已存在；`creo_erase_session_models` 的资格条件（已保存、未被引用等）不覆盖这种“由失败作业产生、未保存、无窗口”的孤儿。只能改名绕过（本次改为 `v10_b_autodim`）。

**建议**：失败回滚时同事务擦除本次新建的会话对象；或对 `execute_plan(model_name=…)` 提供 `on_conflict: "adopt_unsaved"`，仅接管的“无窗口、未保存、有本 job 记录”的对象。

## N1【新发现】`stage` 字段在“被拒后”仍然推进，轮询方无法区分真伪进度

复测 E 时观察到 `creo_get_job(detail=compact)` 的 `stage` 序列为 `connect → executing_feature_plan`，而该作业实际在 `connect` 阶段就 `BUILD_FAILED`（native log `PHASE=connect` 后紧跟 `BUILD_FAILED`）。`stage` 展示的是“runner 计划中的下一步”，不是“已到达的阶段”。对 40+ 操作的大作业，调用方常按 `stage` 估进度；名字被拒这种**必败作业**也会显示 `executing_feature_plan` 数十秒。

**建议**：失败终态时把 `stage` 冻结在真实失败阶段（本例应为 `connect`），或在结果里加 `stage_history`。

## N2【新发现】`retry_after_seconds: 1` 与实际占用时长不匹配，首次重试必然失败

提交 A 例时通道被 `session_status` 探针占用，`creo_execute_plan` 返回：

```
{"status": "busy", "code": "toolkit_busy", "retry_after_seconds": 1,
 "blocking_operation": "session_status", "owner_determined": true}
```

等 3 秒重交才被接受。`session_status` 的快照构建（扫描 120 个 job 目录）实测约 2–4 s，`retry_after_seconds: 1` 是**完成时间估计**（capabilities 里自己也写了 `retry_interval_is_completion_estimate: false`——但回包仍按 1 s 给出）。对手动轮询的调用方，这个值会把第一次重试变成必然的第二次 busy。

**建议**：busy 回包的 `retry_after_seconds` 至少取占用方的历史耗时（`session_status` 上次跑了多久是已知的），或直接给保守的 5 s。

## 0.10.0 里确实变好的部分（验收确认）

1. **端点诊断字段落地（BUG-049/N03）**：`profile.closure_tolerance_mm`、`profile.max_endpoint_gap_mm`、`profile.near_tolerance_pairs{total,truncated,sample}`、`native_section.max_cluster_spread_mm`、`open_end_samples`。本验收输入的闭合质量 4.9e-10 mm 被如实报出。
2. **弧回显补全（T02）**：`arc_geometry[]` 新增 `center_uv` 与 `radius_mm`，失败时也能核对“圆弧到底画在哪”。
3. **切除体积回执**：`cut_bore` 回包带 `material_removed_mm3: 255254.4086`（解析 π·25²·130 = 255254.4798，差 0.07 mm³，0.9.0 同测为 255254.4037）。
4. **预览对空场景的处理（BUG-088/N11）**：本次两例成功作业的 preview 均正常写出（10336 / 12351 bytes，`window_matches_model: true`）。上轮的“空装配预览必失败”不在本轮复测范围，发布说明称已补“空件/实体/钣金对照”。
5. **作业吞吐**：`v10_b_autodim` 的 8 操作计划（含 81 点轮廓 + 8 实例阵列）从提交到 verified 约 68 s，与 0.9.0 同规模作业相当，无回归。

## 对“风扇叶片 L2 方案”的影响评估

发布说明没有新增 `project_curve` / `surface_trim`（上轮 G5），`creo_loft` 仍要求 MCP 自有 XY 草图且 `mode` 只收 `add`（不能放样曲面后加厚），所以 P12 的“放样曲面 → 投影 → 剪裁 → 加厚”链**依旧无法表达**。本轮用 81 点折线叶片 + 5 mm 拉伸 + 8 阵列复测风扇，体积 6 450 293 mm³（0.9.0 同法 3 026 466 → 翻倍的原因是本次轮毂/孔/阵列挂在了同一个模型上，单叶贡献不变）；与 TXT 的 5 743 191 相比的偏差仍主要来自叶片曲面缺失，属于**能力缺口**而非缺陷，维持上轮建议：补 `curve_project` 与 `surface_trim` 两个 op。

## N3【新发现·能力缺口】无外观/颜色 API，装配无法按零件族上色

**现象**：用户要求“给 80 组件装配里的所有零件按零件族上不同颜色”（Strandbeest：曲柄盘/机架板/主轴/连杆/三角板/风扇共 12 族）。逐层核实：

1. 工具层：0.10.0 公开的 94 个工具 / 57 种操作的清单里没有任何 appearance / color 类操作；
2. 源码层：对 `native/*.h`、`native/*.cpp` 全量 grep `appearance` / `ProColormap` / `RGB` / `color`，零命中——native 层没有封装 Creo 的外观 API（ProAppearance* / ProColormap / ProModelColor 相关调用不存在）。

**对照**：SolidWorks 侧的 `Solidworks_AssetMate_MechDog` 有现成的 `recolor_assembly`（按零件族 `{"Crank": [0.88,0.2,0.18]}` 批量上色、dry-run、读回校验），Creo 侧无对应物。

**影响**：80+ 组件的装配在视觉上不可分辨，只能靠预览截图肉眼比对位姿；“按族上色”是装配验收最廉价的目视辅助，也是最常被用户直接提出的请求（本次即真实用户请求）。

**建议**：补一个 `creo_recolor_assembly`（或 `creo_set_appearance`）：
- 最小实现：`ProColormap` 级别的按模型整体着色（`ProMdlColorsSet`），输入 `{model_name: [r,g,b]}`，按 model_id 批量下发；
- 进阶：按 component instance 或面组着色（ProAppearance），支持 dry-run 与读回；
- 注意外观属于显示属性，保存 PRT 时是否持久化（`ProSolidDispPrmSecSet` / appearance file）需要在文档里写明口径。

## 给作者的处理优先级建议

1. **A + D 一起修**：两者是同一个 `SectionRegenerate` 后比对逻辑的两面——coordinates 把“位移>1e-4”当错误，autodim 把同样的位移当成功且不报告。统一成“比对 + 回显 + 可配置闸值”，一次改动同时关掉两个最伤调用方的问题。
2. **E**：失败事务里擦孤儿对象，成本最低、收益直接（本次验收又被迫改名一次）。
3. N1/N2/N3：N1/N2 是轮询协议层面的小修；N3（外观/颜色 API）是纯新增能力，与现有 94 工具无耦合，可放低优先级。
4. B/C/F/G/H 维持上轮报告的建议，本轮证据不变。
