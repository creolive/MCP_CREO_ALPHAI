# 曲面链首次在 Creo 10 打通，但保存间歇失败且新算子判据在 compact 轮询里看不到

> 反馈对象：MCP_CREO_MechDog **v0.13.0**（stable，2026-11-05）
> 对照：v0.11.7（上一轮反馈）→ 0.12.0 → 0.12.1 → **0.13.0**
> 环境：Windows win32 / **Creo Parametric 10.0.0.0**（`release_numeric=42`）/ stdio / mm
> 说明：作者 0.12.0、0.13.0 的实机证据全部来自 **Creo 12.4.0.0**，且 0.13.0 说明第 25、27 行明确写「Creo 10 不要求独立复测」。本报告是这两个版本在 **Creo 10** 上的独立黑盒复验，全部数值来自本机实跑。
> 本轮共 **9 个建模作业**（7 成功 / 2 失败）＋ 2 次提交前门禁拒绝 ＋ 1 次准入拒绝 ＋ 1 次连接恢复；所有结论均附 job_id 或文件路径。

## 0. 结论先行

**这是三轮反馈以来进展最大的一次**：0.3.5 时「8 步里 5 步无工具」的纯曲面链，在 0.13.0 / Creo 10 上已经跑通了最小闭环——

```
surface_fill → datum_plane → surface_trim → thicken → 实体
800 mm²  →  700 mm²  →  1400 mm³（= 700 × 2），质心 (22.5, 10, 0)
saved_file_reloaded_and_verified = true
```

上一轮报告里那条「`quilt_feature` 引用 trim 结果 → `ProFeatureGeomitemVisit -4` → 无法缝合」的断链，**已随 `inspect_model(section="quilts")` 落地而解开**。三个新算子（`surface_trim` / `surface_offset` / `project_curve`）在 Creo 10 上全部实测通过，定量结果与发布说明的 Creo 12.4 数字一致。

但本轮同时暴露两个必须处理的问题：

| 级别 | 问题 | 影响 |
|---|---|---|
| **P0** | `ProMdlnameBackup` 间歇返回 −1，且**回滚也失败**、模型卡在 `status=failed` | 9 个作业中 2 个；原生操作全成功、几何数值正确，却拿不到保存结果 |

## 3. 仍不可用：整链还差「放样 + 缝合」

### 3.1 `quilt_merge` 仍门禁

```
Error: Not available in the 0.13.0 release; no native job was queued.
quilt_merge: the surface merge is not published: on this machine the
documented ProMerge.h array tree creates an ACTIVE feature that owns four
PRO_SURFACE items and no PRO_QUILT item whatever the merge type (JOIN or
INTERSECT) and geometry (touching or truly intersecting), the quilt visit
answers -4 ... the joined area and closure cannot be measured or handed to thicken
```

作者在 `docs/work-items/FEAT-039.md` 也记为「S03 缝合仍 gated——路线已排除，待新路线」，且 `capabilities.unavailable_operations.quilt_merge` 有同样说明。**状态透明，不是回归**；但从调用方看，任务书「修剪 → 缝合 → 实体化」的缝合一步仍然没有工具。

发布说明第 18 行给出的替代路线（两片各加厚 2 mm 合入同一 body，重叠只算一次，体积 2800 mm³）本轮**未实跑**，无法确认在 Creo 10 上成立。

### 3.2 `loft(mode="surface")` / 边界混合仍被拒

`LoftOp` 的 schema 现在确实有 `mode: Literal["add","cut","surface"]`（`schema.py:851`），但提交两截面圆形放样曲面时：

```
Direct Blend supports solid add into the default body only; cut, surface and
new_body are not accepted - the 2026-11-05 measurement on the seed reference
part shows the blend feature has no extractable element tree
(ProFeatureElemtreeExtract returned -18), so the panel route is the only route
```

作者在 `G5-NATIVE-CONTRACT.md:422` 已写明：「剩下的可靠路线只有一份参照树（在 Creo 里手工建一个 Boundary Blend，再用 `dump_tree` 读回元素树）」。

**这仍是任务书纯曲面法最后一块硬缺口**：五爪需要「两个 50° 扇形截面做放样」，而多截面曲面放样 + 缝合都不可用。当前可做的是 `surface_trim` + `thicken` 的"面→实体"链，不是完整曲面法。

> 建议：把 `loft` 的 `mode` 在 schema/capabilities 里同步标注为「solid add only」，避免调用方看到 `mode:"surface"` 就以为可用；或按 FEAT-039 的参照树路线推进 `boundary_blend`。

## 4. 本轮发现的问题

### 4.1 【P0】`ProMdlnameBackup` −1 间歇失败，且回滚失败、模型卡在 `failed`

**9 个作业里 2 个**，都是「原生操作全部成功、几何数值正确，倒在 `save_and_reload`」：

| job | 操作 | 原生结果 | 失败点 | 回滚 |
|---|---|---|---|---|
| `a404adae893446de8ace085cc1807d27` | 在已有模型追加 `datum_plane` + `surface_trim` | 两者 `succeeded=true`，feature 87 创建/再生均 0 | `ProMdlnameBackup(board, destination) = -1` | `rollback_succeeded=false`，`"Saved feature/body count changed"` |
| `7257892985664b66b3942c7a186efdea` | 在已有模型追加 `thicken` | `volume_after_mm3 = 999.9999999999998`（500 mm² × 2，正确） | 同上 | 同上 |

失败后模型状态：

```json
{"status":"failed", "revision":1, "pending_job":null,
 "last_job":"a404adae…", "snapshot":{"mutation_pending":false}}
```
即**没有任何 pending job 可等**，必须走 `creo_reconcile_model` 才能继续用这个模型。

**非确定性**：同样的「已有模型 + 追加 trim」在 `job 3612d38e…` 成功（revision 1→2，`.prt.3` 落盘）；同样的「fill→trim→thicken」在 `job 1ea073b2…` 一次建到底也成功。因此**触发条件尚未定位**，本报告不把它归因为某一种操作。

已排除的因素：
- 原生层：`ProFeatureWithoptionsCreate=0`、`ProSolidRegenerate=0`、所有 `ProFeatureStatusGet/IsIncomplete` 通过，`verify_model_assertions` 通过；
- 目标文件不冲突：失败后 `output/` 里没有 `.prt.3`/`.prt.4` 残留；
- 不是 Creo 模态框：窗口枚举只有主窗口与「检索」进度窗，无阻塞对话框。

`jobs/a404adae…/native.log` 的关键行：
```
PHASE=save_and_reload
STAGE name=verify_model_save elapsed_ms=0 since_start_ms=5759
ProMdlnameBackup(board, destination)=-1
BUILD_FAILED=-1
PHASE=rollback_to_saved_checkpoint
```

**建议（三条，按收益排序）**：
1. 把 `destination` 的实际路径、`-1` 的子原因（文件已存在 / 权限 / 模型在会话中状态）写进 `failure_reason`，现在只有一行裸码，无法区分是备份目标问题还是模型状态问题；
2. 回滚不要只用「Saved feature/body count changed」这一个判据就宣告失败——本例原生侧已经把特征删回去了，`counts` 差异来自「从无到有」的合法语义变化。至少给出 `recovery` 字段明确指向 `creo_reconcile_model(ack_failure|accept_saved)`，并在终态 `next_steps` 里带上；
3. 若备份是幂等重试可解（例如目标版本号竞争），在 `save_and_reload` 内部做一次带证据的重试，而不是直接把模型推到 `failed`。

### 4.2 【P1】三个新算子的判据字段在 `detail=compact` 全部不可见

`get_job(detail=compact)` 的 `operations[]` 对三个新算子只给 `succeeded / execution_status / effect_status`（`thicken` 多给体积前后值）。发布说明宣称的判据字段全部只存在于 `native_result.json` / `job.json`，需要**第二次请求** `detail=full, section=operations_result` 才能看到：

| 算子 | compact 可见 | 仅 full 可见 |
|---|---|---|
| `surface_trim` | `succeeded` | `area_before_mm2` / `area_after_mm2` / `*_status` / `kept_side_basis` / `kept_side` |
| `surface_offset` | `succeeded`, `volume_before/after` | `measured_offset_distance_mm` / `source_area_mm2` / `offset_method` / `target_quilt_id` |
| `project_curve` | `succeeded` | `curve_id` / `curve_length_mm` / `endpoints_mm` / `helper_feature_id` / `route` / `direction_basis` / `curve_candidates` |

实测：`job 4db5fb32…` 的 `job.json` 里有 `"area_before_mm2":800.0,"area_after_mm2":700.0`，但同一 job 的 compact 回执里完全没有；`job 3f4c8c36…` 的 `measured_offset_distance_mm=4.999999999999999` 同理。

**为什么这条重要**：`get_job` 至今没有长轮询（§4.3），调用方的标准姿势就是反复 `detail=compact` 轮询。按这个姿势，调用方会得出「算子成功了，但没给任何可验证数据」的结论，进而误判为不可验收——而 0.13.0 最核心的改进恰恰是这些实测判据。

**建议**：把上述三组字段加进 compact 白名单（每组约 3–6 个标量 + 一个 status 对象，远低于 32 KiB 预算）。作者 0.12.0 已经为 `planar_wall` 做过同类处理（发布说明第 13 行「compact 与 full 轮询都能看到该块」），照此办理即可。

3. 澄清「无新增原生编译要求」的措辞（是指"无需用户手动编译"还是"原生代码未变"）。
