## 1. 阻塞性问题 N-1【严重】升级后 Toolkit 会话断连，官方恢复路径无法自愈，实机验收 100% 被阻塞

`creo_check_environment` 在这期间始终 `ready_to_build=true`、全部 SDK 检查 `exists=true`；即**静态环境检查全绿，但实际一条建模作业都提不进去**。

### 1.2 为什么这是 MCP 的问题而不只是 Creo 的问题

- 工具已能精确观测到 `parametric.exe` 存在 hung top-level window、IPC 不可读、worker 退出码 20，但给调用方的只有一段通用文字「检查 Creo 是否有活动的 feature Dashboard 或模态警告框」；**没有 `failure_code`、没有窗口标题、没有可执行的下一步**，而服务自身明确「never closes Creo / never restarts」。
- 恢复链**不可操作**：`retry=true` 之后约 2 分钟只能反复读到 `checking → waiting_for_connection`，期间 `retry_allowed=false`；没有 retry id、没有预计完成时刻、没有失败原因码，只有两套含义未说明且不断递减的预算（`remaining_budget_seconds` 与 `phase_remaining_budget_seconds`）。调用方无法判断「该继续等」还是「该让人去 Creo 界面手动处理」。
- `launch_attempt` 全程固定为 **29**，没有随本轮 `retry=true` 递增，也无法从返回中判断本轮重试是否真的发起过一次启动/探测。
- 这不是孤例：仓库内已有 `2026-10-26…0.6.1-会话断连同族故障复现`、`2026-10-30…0.8.5-会话卡死第三次复现`，以及 0.13.0 安装验收文档 §1 的「**BUG-001 卡死根因未定，实机验证冻结**」。**跨 0.6.1 → 0.8.5 → 0.13.0 多版未根治**，且 0.13.0 的发布验收因此把全部运行时能力标为「未验证」。

### 1.3 建议

1. 给 `creo_startup_status` 一个**机器可读的终态/进度回执**：`retry_id`、`phase`、`failure_code`、`started_at`、`next_allowed_retry_at`、`terminal_reason`；`retry_allowed=false` 时说明「谁在占用、预计何时可变 true」。
2. 检测到「Creo 进程存活 + Toolkit IPC 不可读 + `hung_window_observed=true`」时，直接报 `creo_modal_dialog_suspected`，并带上可核查的 **PID / 窗口标题 / 窗口可见性**，而不是让调用方去猜哪个对话框。
3. 提供一个**受人工显式确认保护**的最小「重建会话」动作（当前 `next_steps` 只有 `operator` 文字建议，无任何可执行入口）；至少让「确认 → 断开旧 IPC → 重新连接」不必靠关掉整个 Creo。
4. 把 BUG-001 的根因定位列入发布门槛；否则「编译通过 / 注册稳定 / 版本 up_to_date」与「能不能建模」之间长期脱节。

## 3. 其余新发现

- **N-2【中】P-1 的文档修复只覆盖独立工具，不覆盖 `creo_execute_plan`**。建议把 `server.py:1963-1965` 的约定文本同步写进 `AssembleOp.rotation_matrix` 与 `ComponentPlacementOp.rotation_matrix` 的 `Field(description=...)`（这样 JSON Schema 会自动带出），并在每个成功组件的结果里回显 `rotation_convention: "row_vectors"` 与读回的 4×4 `transform`。目前工具 docstring 写了、schema 不写，客户端按 schema 生成代码时仍然只能靠踩坑发现。
- **N-3【中】`creo_list_jobs(detail=compact)` 内联原生日志尾**。建议 compact 只保留 `job_id / status / stage / created_at / finished_at / message（截断 200 字）/ result.success / failure reason`；`native_log_tail` 仅在 `detail=full` 或显式 `include_native_log=true` 时返回。`limit=10` 的常规轮询会把 ~80 KiB 日志塞进一次响应。
- **N-4【低】`creo_get_job(compact)` 的 `component_changes` 只给 20/35 条样本，`truncated=true`，但 compact 模式没有给出取全的路径**（`section` / `cursor` 被限制为 `detail=full` 才能用）。与 `detail=full` 的分页契约不一致，建议 compact 里直接给 `full_detail_hint` 或允许 compact 也分页。
- **N-5【观察，非缺陷】** `capabilities` 的 `registered_operations` 含 `quilt_merge` 而 `operations` 不含、`unavailable_tools=["creo_quilt_merge"]`、`unavailable_operations` 有详细原因说明，标注是清楚的；但 compact 摘要里没有 `gated` 标记，调用方仍可能误提交必然失败的算子。

## 4. 明确未验证项（不得外推为通过）

1. 任意自转角（正交、det=+1）的 `rotation_matrix` 在 `creo_execute_plan` 装配中是否仍触发 `ProAsmcompAssemble -2` 与整批回滚；失败项是否已回填 ProError / matrix echo。
2. 共面/相切叠加的 `extrude` 失败，是否新增 `failed_label` / `failed_sketch` / ProError 码 / 成因提示。
3. `through_all` 切除方向未命中材料时的诊断，以及 `depth` 是否仍被要求/回显。
4. `creo_execute_plan` 提交响应体大小（P-11）。
5. 0.13.0 新增曲面算子（trim / project_curve / surface_offset / solidify）在 Creo 10 的运行时行为；本轮只确认了接口存在与 schema 文本。
6. 在 0.13.0 下重新打开 `asm_v2.asm.3` 并做 live inspection / 重算包围盒与 8.5 四个锚点；本轮仅完成了 managed 记录与已保存检验快照的读回。

> 注：`src/creo_mechdog/schema.py` 的校验器、`server.py` 的 docstring、`capabilities.py` 的说明都属于**静态契约证据**，只能证明「代码里写了/校验了」，不能证明「在 Creo 10 内核上跑通了」。
