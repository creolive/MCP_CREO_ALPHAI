## 4. 本版发现的问题

### 4.1 【P1】`native/surfaces.cpp(168)`：`ProQuiltInit` 返回码被丢弃，新增曲面偏置缺少错误检查

本机 MSVC 14.44.35207 编译首次报出：

```
native\surfaces.cpp(168): warning C4552: '!': 运算符不起任何作用；应输入带副作用的运算符
```

对应源码（`generic_surface_offset`，本版新增 `creo_surface_offset` 的源面积测量路径）：

```cpp
static void generic_surface_offset(const J &op) {
    ...
    double source_area = 0.0;
    bool area_known = false;
    {
        ProQuilt quilt = nullptr;
        if (!ProQuiltInit((ProSolid)board, quilt_id, &quilt); quilt) {   // ← 168
            MeasurementOutcome area = quilt_area_native(quilt);
            if (area.available) { source_area = area.value; area_known = true; }
        }
    }
```

**问题**：这是 C++17 `if (init; condition)`。`init` 中的 `!ProQuiltInit(...)` 是一个**被丢弃的布尔表达式**——`!` 的结果没有任何作用（这正是 C4552 的含义），实际条件只剩 `quilt != nullptr`。也就是说：

- `ProQuiltInit` 的 `ProError` 返回码**从未被检查**；
- 若初始化失败但 `quilt` 被部分赋值/非空，仍会进入 `quilt_area_native(quilt)` 测量无效面组；
- 该 `source_area` 随后用于本版对外承诺的 `measured_offset_distance_mm = 体积 ÷ 源面积` 实测判据，错误面积会污染返回字段。

**对照证据**：同包 `native/quilt_merge.cpp:63/67` 写的是正常的 `if (!ProQuiltInit(...))`（作为条件，有效），说明作者本意是检查错误码，`surfaces.cpp` 这处是改用 `if`-init 语法时漏写条件。全仓 `grep -rn '!ProQuiltInit' native/` 仅这 3 处，只有 168 行受影响。

**建议**（任选其一，并补一条单测覆盖「Init 失败但指针非空」）：

```cpp
// 方案 A：显式错误码
if (ProError st = ProQuiltInit((ProSolid)board, quilt_id, &quilt);
    st == PRO_TK_NO_ERROR && quilt) { ... }

// 方案 B：回到普通条件
ProError st = ProQuiltInit((ProSolid)board, quilt_id, &quilt);
if (st == PRO_TK_NO_ERROR && quilt) { ... }
```

同时建议把 `/W3` 下的 C4552 提升为发布阻断（或在 `dev_check.py` 里扫描编译日志的 `warning C4552`），避免同类「表达式被丢弃」再次静默进入发布包。

> 本项**仅由编译警告 + 源码静态分析得出**，未做 Creo 实机复现（受 §1 冻结约束），不宣称已观察到错误面积或错误返回值。

  - `gh` **未安装**（`command -v gh` 无输出）；
  - `github.com` 直连失败（先 `curl: (28) Failed to connect ... port 443`，后 `curl: (52) Empty reply from server`）；

  1. 在 `tools/package.py` 产出两个 ZIP + 两个 sidecar 后直接调用 `validate_directory(staging_dir, version)`，让「四附件齐全且摘要一致」成为**打包阶段**硬闸门（无需网络）；
  2. `--tag` 模式在 `gh` 缺失或下载失败时给出明确降级提示「可改用 `--dir`」，而不是只报 `gh release download failed`；
  3. `download()` 增加不依赖 `github.com` 的备用通道（GitHub API asset 端点 / `Accept: application/octet-stream`），或至少在文档中说明该环境限制；

### 4.4 【P3】sidecar 为 CRLF 行尾，标准 `sha256sum -c` 在 Git Bash / Windows 下直接失败

```
$ sha256sum -c MCP_CREO_MechDog-0.13.0-source.zip.sha256
sha256sum: 'MCP_CREO_MechDog-0.13.0-source.zip'$'\r': No such file or directory
MCP_CREO_MechDog-0.13.0-source.zip: FAILED open or read
```

sidecar 内容本身完全正确（`4033784a…e03b  MCP_CREO_MechDog-0.13.0-source.zip`），但文件以 CRLF 结尾，`\r` 被当成文件名一部分。去掉 CR 后两个 ZIP 均 `OK`：

```
$ tr -d '\r' < xxx.sha256 | sha256sum -c -
MCP_CREO_MechDog-0.13.0-seed-library.zip: OK
MCP_CREO_MechDog-0.13.0-source.zip: OK
```

`check_release_assets.py` 内部用 `read_text().splitlines()` + `line.strip()`，能容忍 CRLF，所以**工具本身没问题**；受影响的是遵循「标准 sha256sum 校验」的升级者。建议在 `tools/package.py` 写 sidecar 时固定 `\n`（`newline="\n"` 或写 bytes），并在 `INSTALL.md` 的升级命令里给出 `tr -d '\r'` 的兼容写法。

`creo_quilt_merge` 作为 `@mcp.tool` 注册，但 docstring 与 `capabilities.py` 明确其提交必被拒绝（需 live acceptance）。客户端会在工具列表里看到一个**必然失败**的算子。作者已如实标注，不算隐瞒；建议后续在 `creo_capabilities` 的 compact 摘要里直接给出 `gated` 标记，减少调用方误用。
