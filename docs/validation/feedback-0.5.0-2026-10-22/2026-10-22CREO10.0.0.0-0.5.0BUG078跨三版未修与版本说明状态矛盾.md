## 2. 🔴 核心问题：BUG-078（P1）跨三版未修，且没有排期

### 2.1 现状（作者披露 + 本轮静态确认）

`docs/work-items/BUG-078.md` 当前状态：

```
优先级：P1
状态：已复现（0/4 实机；机理部分定位，修复方案待定）
目标版本：待排期（0.4.7 发布不阻断；BUG-077 第 2 组恢复链路验收中 accept 两动作被本条阻断）
```

0.4.7 与 0.4.8 的版本说明都在"已知问题（随版披露）"里原样保留了这条：

> `accept_saved` / `accept_live` 实机不可用（实机 0/4，该路径历史从未实机通过）；
> 同日普通编辑路径另有 3 次偶发 `ProMdlnameBackup -1`，与成功样本操作同构，未定位根因。

### 2.2 为什么建议优先排期

1. **它是 P1，且是"核心恢复能力的正面路径"不可用**。`accept_saved` / `accept_live` 不是边缘场景，
   而是 `creo_reconcile_model` 恢复工作流里把"现场"确认为基线的标准动作。这条路径不可用，
   意味着恢复功能实际只剩 `restore_baseline` / `abandon_new` 两条退路 —— 对 dirty 现场（现场≠基线）会**卡在保护挂起**。
2. **历史从未实机通过**（作者原话"BUG-055 记录的 accept_live 实机正向路径未验证，与本次发现一致"）。
   说明它不是新引入的回归，而是**长期潜伏**，只有这次凑齐条件才被暴露 —— 这类问题越晚修越贵。
3. **跨 0.4.7 / 0.4.8 / 0.5.0 三版未修，且"目标版本待排期"**。同一时段内项目修了 BUG-077、
   新增了 FEAT-045/046/047、做了 DEV-027 双维度盘点 —— 交付速率很高，唯独这条 P1 没有落到任何版本上。
4. **有 3 个 dirty 现场模型保护挂起中**（`de6f0bb5` / `bebe7e2b` / `57294ff8`）。
   本机虽未连 Creo，但可以推想：普通用户一旦踩到，会永久遗留三个无法收尾的挂起模型，缺少自助手段。
5. **同一 API 的另一路径也在偶发同一底层错误**："同日普通编辑路径另有 3 次偶发 `ProMdlnameBackup -1`"。
   `ProMdlnameBackup` 是备份动作，若普通编辑也会偶发失败，影响面可能比"仅恢复路径"更大。

### 2.3 建议

1. **给一个排期或明确的"不修"结论**。哪怕写"0.6.0 处理"，也比"待排期"更便于下游规划；
2. 在 BUG-078 里补一条**用户侧自助出路**：dirty 现场卡在保护挂起时，用户能做什么（保留现场、如何导出诊断、
   是否可用 `abandon_new` 收尾而不丢原件）。当前只有"保护语义正确保留"的技术描述，缺操作指引；
3. 若能确认 `ProMdlnameBackup -1` 的机理（"部分定位"），建议先出一个**只在失败时返回更多上下文**的中间版本
   （返回值、路径、当前模型名/版本、是否有同名文件、是否只读目录），便于外部环境抓现场。

## 3. 🟠 次要问题：0.4.7 / 0.4.8 版本说明写"未发布"，但实际都已发布

两版 `docs/RELEASE_NOTES_*.md` 的标题与正文都明确声称"未发布"：

- `docs/RELEASE_NOTES_0.4.7.md` 标题：`# MCP_CREO_MechDog 0.4.7 版本说明（开发分支，未发布）`
  正文：`当前仅更新开发分支源码版本，未合入 main、创建标签或发布 Release。`
- `docs/RELEASE_NOTES_0.4.8.md` 标题：`# MCP_CREO_MechDog 0.4.8 版本说明（开发分支，未发布）`

**但 GitHub 上两个 Release 都真实存在**：

| Tag | published_at (UTC) |
| --- | --- |
| v0.4.7 | `2026-10-22T01:06:19Z` |
| v0.4.8 | `2026-10-22T02:23:48Z` |

### 影响

- 用户/自动化脚本读到"未发布"会**跳过这两个版本**（本次我确实是从 0.4.6 直接跳到 0.5.0 的）；
  而 0.4.7 实际带来了 `creo_migrate_registry`、`creo_registry_health` 两个工具和 BUG-077 拆分，
  0.4.8 带来了 DEV-027 双维度盘点 —— 这些能力在 0.5.0 里当然也包含，但读者无从判断"我该不该等这两个版本"。
- 与项目自身 `RELEASING.md` 要求的"合入 main 必须同流程发布 Release"形成叙述冲突，
  削弱版本说明作为事实记录的可信度。

### 建议

1. 发布时把"（开发分支，未发布）"这行改为实际状态（如"已发布为 Pre-release"），或直接删掉；
2. 若确实存在"先在 main 上写说明、后发布"的流程，建议说明写"待发布"而非"未发布"，发布后回填；
3. 发布检查单加一条：`grep -i "未发布" docs/RELEASE_NOTES_<ver>.md` 必须无命中（或与 Release 状态一致）。
