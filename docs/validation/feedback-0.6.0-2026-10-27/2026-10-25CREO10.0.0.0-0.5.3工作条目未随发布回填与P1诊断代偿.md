## 2. 🔴 核心问题：工作条目的"状态/目标版本"未随发布回填

### 2.1 具体证据

| 条目 | 卡内原文（第 3 行） | 实际情况 |
| --- | --- | --- |
| **BUG-079** | `状态：已修复，WorkBuddy 复验通过（待发布）。目标版本：下一未发布 PATCH（建议阻塞合入）` | **0.5.1（10-23）已交付** —— `RELEASE_NOTES_0.5.1.md` 中 BUG-079 出现 2 次，明确列出"就地修改圆弧半径不再导致草绘特征再生失败" |
| **BUG-081** | `目标版本：0.5.3（目标，未发布）` | **0.5.3（10-25）已正式发布**（`prerelease=false`），且本版正是交付该条诊断的版本 |
| **BUG-082** | `目标版本：0.5.3（目标，未发布）` | 同上；且该条**本体未修**（见 §3），"目标版本"本身也已失效 |

### 2.2 为什么值得提（同类问题第二次）

我在 **2026-10-22** 的报告里报过同一类问题：`RELEASE_NOTES_0.4.7/0.4.8` 写"（开发分支，未发布）"但实际都已发布。
作者处理得很好 —— 给版本说明加了明确的回填行：

```
发布状态：已发布。2026-10-22 合入 main 并发布 GitHub Release（Release 420203117，Pre-release，非草稿）……
本说明撰写于 2026-10-21，当时状态为开发分支、未合入未发布，以下历史日期与陈述保持原样。
```

**但同样的处理没有扩展到 `docs/work-items/*.md`。** 结果是：版本说明现在可信，工作条目仍会把读者带到"这版还没发"的错误结论上。
对下游用户来说，`RELEASE_NOTES` 与 `work-items` 是两套并行的信息源，**只修一半等于把不一致从一处挪到另一处**。

### 2.3 建议

1. **把已有的发布检查单从 RELEASE_NOTES 扩展到 work-items**：发布时对本次交付的每个 ID 回填
   `状态：已发布 <ver>` 与 `目标版本：<ver>（已发布）`，或加一行 `交付：<ver> @ <date>`；
2. 加一条可自动化的 grep 校验（与上次那条同类）：
   `grep -rn "未发布\|待发布" docs/work-items/*.md` 命中项必须属于"确实未发布"的条目；
3. 更省力的做法：把 `目标版本` 与 `状态` 的"发布事实"部分**集中到一个 `docs/DELIVERY.md` 索引**（ID → 版本 → 日期），
   work-items 只写技术状态。这样发布时只改一处，不会多点失同步。

## 3. 🟠 观察：三个 P1 本版都以"加诊断"交付，其中 BUG-082 本体未修

0.5.3 的 P1 覆盖情况：

| 条目 | 本版交付内容 | 本体状态 |
| --- | --- | --- |
| BUG-081 | `owner_block` / `blocked_entries` 有界诊断 + `next_steps` 指引 | 属"诊断类"条目，交付即达标 ✅ |
| BUG-082 | `failed_features` 逐特征诊断（id/名称/类型/状态/incomplete/geometry_items） | ❌ **再生失败本体仍在**：`ProSectionSolve=-1` → `REV_SK/REV1 status=6`；autodim 改角 90°→80° 仍失败 |
| BUG-078 | 无代码改动，根因定位为会话级损坏 | ❌ 三个 dirty 现场仍只能 `restore_baseline` |

**评价**：如实披露（在"已知问题"里逐条列明）是值得肯定的，`failed_features` 也确实让抓现场容易了。
但从使用者角度看，"能诊断出失败"和"不失败"是两件事：
`BUG-082` 的 autodim 改角**是常规建模动作**（把角度从 90° 改成 80°），失败会直接打断编辑流程，
而 `coordinates` 路径成功 —— 意味着**用户只要知道换标注模式就能绕过**，这个绕过办法目前只写在条目里，
没有出现在面向用户的文档（README / 编辑相关说明）中。

**建议**：
1. 在 README 或编辑指引里写一条**已知限制 + 立即绕过**（"autodim 改角可能再生失败，改用 coordinates 或改半径"），
   让用户不必读工作条目；
2. `BUG-082` 的"目标版本"既然已经过期，请明确下一个目标版本或"待定位根因后再定"，
   避免又出现 §2 那类"目标版本已发布但未修"的记录。
