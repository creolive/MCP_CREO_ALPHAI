## 2. 🔴 核心问题：仓库级换行归一化已波及 `native/third_party/`，差一个文件就重演 0.4.0

### 2.1 实测证据

用 0.5.3 回滚包与本版逐字节对比（同一台机、同一 SDK/config），本版有 **79 个文件属于"仅换行差异"**（CRLF↔LF），
明显是一次**仓库级行尾归一化**。其中落在 `native/` 下的只有一条：

```
native/third_party/LICENSE.nlohmann-json     ← 仅换行差异
```

而 `native/third_party/json.hpp` **恰好 SAME**（未被这次归一化波及）。

**这正是 0.4.0 事故的同构场景**：当时 `json.hpp` 仅 CRLF→LF 差异，就让 loader/payload 指纹换代、
`protk.dat` 重新生成、用户注册失效一次。本次归一化**已经把 `third_party/` 目录当作普通文本目录处理了**，
只差 `json.hpp` 一个文件没被扫进去 —— **注册稳定是靠运气，不是靠机制保证**。

### 2.2 结论

我在 0.4.0 / 0.4.1 / 0.4.2 三次报告里建议过"把 `json.hpp` 移出 loader/payload 指纹清单"（或指纹前归一化）。
0.4.4 落地的是"指纹按 CRLF→LF 归一化内容计算（`sha256-repo-lf-v1`）"——
**这个方案本身能扛住换行变化，所以本次没炸**。但请注意：

- 当前算法对"换行"安全，**对其它字节级变化（BOM、末尾空行、编码）不安全**；
- 本次归一化说明仓库里存在**批量改写文本文件**的例行操作，`json.hpp` 迟早会被扫到；
- 一旦被扫到且改动不止换行（例如格式化工具顺带改了空白），仍会触发注册失效。

**建议（成本最低的一条）**：在 `.gitattributes` 里对 `native/third_party/**` 显式固定 `-text`（不转换），
并在发布检查单加一条校验：`native/third_party/json.hpp` 的 SHA256 与上一版一致，否则必须在版本说明里显著提示"需重新注册回调"。
这样至少把"静默失效"变成"显式告知"。
