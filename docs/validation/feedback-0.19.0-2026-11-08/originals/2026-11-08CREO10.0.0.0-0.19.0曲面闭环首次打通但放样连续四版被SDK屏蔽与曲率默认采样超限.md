## 1. 结论先行

**本版是曲面链路进展最大的一版：`creo_quilt_merge` 解禁后，Creo 10 上首次打通「曲面 → 两两合并 → 闭合壳 → 实体化」完整闭环。** 这是 0.17.4 / 0.18.2 / 0.18.4 三轮始终卡在 `ProQuiltVolumeEval=-18 / quilt_is_open` 的那道门。作者基于 Creo 12.4 的 H03/H08/H10 三项核心结论，在 Creo 10 上均取得独立正证据，且关键数值逐位一致。

但**原始任务「可乐瓶五爪花瓣瓶底 · 全程曲面法」在 Creo 10 仍不可完成**，因为闭环打通只解决了「缝合/实体化」，没解决「造出五爪曲面」：

1. **P0（连续第四版未修）**：`creo_surface_loft` 在 Creo 10 SDK 上仍被 `Probbl.h` 缺失的 `__has_include` 守卫编译屏蔽，操作体根本没进 worker；任务书第 2 步「两个 50° 扇形截面放样」无法执行。
2. **P0（0.18.4 已报，未修）**：任务书第 4 步「用爪面修剪半球底」的开放带面交线诊断缺失，开放弧无法分割 quilt。
3. **P1（未修）**：`creo_surface_boundary_fill` 仍在 `unavailable_tools`，爪谷 G1 桥接、中心 R8 凹球封闭没有曲面级实现。

另外新发现两项**只有 WorkBuddy 黑盒才会暴露**的可用性/契约问题：`creo_measure_surface_curvature` 默认 12×12 采样单次返回 **97,987 字符**，直接超出 MCP tool-result 上限；`creo_quilt_merge` 的公开 docstring 仍写「gated / 结果字段不可见」，与实测完全相反。

## 6. 本轮发现的问题清单

### 6.1 【P0】`creo_surface_loft` 在 Creo 10 SDK 连续第四版被编译屏蔽

**证据**

- `native/surface_loft.cpp` 仍带本地补丁：

```cpp
// LOCAL PATCH (Creo 10 SDK): <Probbl.h> is absent on this SDK generation.
#if defined(__has_include)
#  if __has_include(<Probbl.h>)
#    define MECHDOG_LOCAL_HAS_PROBBL 1
#  endif
#endif
#ifdef MECHDOG_LOCAL_HAS_PROBBL
#include <Probbl.h>
#endif
...
#else  // no Probbl.h on this SDK generation (Creo 10)
    "surface_loft requires Probbl.h, which this Creo Toolkit SDK does not ship; "
```

- `D:/Program Files/PTC/Creo 10.0.0.0/Common Files/protoolkit/includes/Probbl.h` 确认**不存在**；`native/surface_boundary_fill.cpp` 也有同样的 `#else // no Probbl.h ... (Creo 10)` 降级。
- 实跑作业 `8a48a76a5e974792b0f378f7fd08b612`（两个合法的单曲线 sketch `sk_l1` / `sk_l2`）：

```text
status=failed, stage=execute_surface_loft, toolkit_code=-1
message: "surface_loft requires Probbl.h, which this Creo Toolkit SDK does not ship;
          the boundary-blend element tree is unavailable on this SDK generation"
rollback_succeeded=true, terminal_effect.managed_model.effect=rolled_back
```

**影响**：`capabilities.families.surface_loft.enabled=true`、`surface_chain.tools` 也列出它，但 Creo 10 上该工具 100% 失败。任务书第 2 步与作者 H10 整链的五片锥扇面都不可用。

**建议**：Creo 10 的 `ProElemId.h` 已有 34 个 `PRO_E_BNBLN_*` 常量（`PRO_E_BNBLN_1DIR=651`、`2DIR=652`、`DIR_CURVES=657`、`CURVES=661`、`RULED=1206`、`TAN_COND=459` 等），可考虑不依赖 `Probbl.h` 的等价元素树；若确实无法支持，至少让 `capabilities` 按 SDK 代际返回 `enabled=false` 并在 tool 描述中写明「Creo 10 不可用」，避免能力面与实机不符。

### 6.2 【P1】`creo_measure_surface_curvature` 默认输出超出 MCP tool-result 上限

**证据**：单面、`samples_per_direction=12`（默认值）返回 **97,987 字符**，客户端报 `result exceeds maximum allowed tokens` 并转存文件；改为 `5` 后才可直读。体积来自 `faces[].points[]`（144 项/面，每项含 `status` 对象与两个方向向量）。

**影响**：这是新公开工具在真实 MCP 黑盒下的默认失败路径；作者发布说明的「WorkBuddy 公开 MCP 黑盒验收未执行」正好漏掉这一层。`get_job` 已有 `sections` / `limit` / `cursor` 分页机制可复用。

**建议**：增加 `include_points: bool = false`（或 `detail="summary"` / `points_limit` + `cursor`），默认只返回 `summary`、`g1_*`、各面 `max_abs_curvature_per_mm` / `min_curvature_radius_mm` 与状态；需要逐点数据时再显式开启分页。

### 6.3 【P1】失败作业 `connect` 计时被 8192 B tail 窗口截断（0.17.4 起第 4 版未修）

本轮三个失败作业均复现 `native_progress.stages_seen=0, reason="no_current_stage_timing"`，而同一份 `result.verify_stages` 里明确有 `connect` / `connected`：

| 作业 | `log_bytes` | `STAGE connect` 字节位置 | `STAGE connected` 字节位置 |
| --- | --- | --- | --- |
| `ffa962e7…`（round 负例） | 8,988（`native.log` 实测 8,774） | 14 | 107 |
| `8a48a76a…`（surface_loft） | 10,228 | 前部 | 前部 |
| 0.17.4 `25c44c7f…`（历史样本） | 8,469 | 15 | 110 |

`src/creo_mechdog/native_stage.py` 仍为 `TAIL_BYTES = 8192`，tail 起点 `max(0, len-8192)`（如 8,774 B 日志起点 582），两个 STAGE 全在窗口外。

**建议**：把 `verify_stages` 作为阶段计时的首选来源（它已在结构化结果里且完整），`native.log` tail 仅作补充；或让 `stall_report` 同时保留文件头部 N 字节。

### 6.4 【P1】合并后残留 quilt 干扰曲面组闭合检测

`quilt_merge` 成功后 `inspect_model(section="quilts")` 仍返回 **2 个 quilt**（`counts.quilts` 也未下降）。被消耗的 `quilt 127`：

```json
{
  "quilt_id": 127, "face_count": 1,
  "area_mm2": null,
  "area_status": {"available": false, "query_code": -4, "reason": "contour_area_eval_failed"},
  "closed": true, "closed_status": {"available": true, "query_code": 0},
  "bbox_mm": [[20,0,0],[40,20,0]]
}
```

一个**面积不可测**的残留片被标成 `closed=true`。对「全程曲面法」第 7 步「缝合公差 0.01 + 闭合检测」来说，调用方若遍历所有 quilt 做组级判断，会把残留片算成已闭合成员。作者发布说明也承认「被消耗的工具 quilt 在内核里留下不可测记录（属内核行为）」，但公开面没有 `consumed` / `residual` 标记。

**建议**：在 `quilt_merge` 回执中给出 `consumed_quilt_id`，并让 `inspect_model(section="quilts")` 对这类条目返回明确状态（如 `state="consumed_by_merge"`、`closed=null` + `reason`），而不是把 `closed=true` 与 `area=null` 并列输出。

### 6.5 【P1/P2】`creo_measure_surface_group` 在特定 quilt 上抛工具级异常，无结构化回执

模型 `petal_0190_merge` 的 `quilt 82`（合并目标、已 `thicken` 2 mm）上连续两次调用：

```text
Error executing tool creo_measure_surface_group:
surface_group_measure could not visit the group boundary: contour_edge_visit_failed
```

- 传两个 quilt（82 + 残留 127）与只传 82 都失败，**不是多 quilt 组合问题**；
- 两个失败也生成了 job 记录（`4f8690df…`、`37a062be…`，status=failed）；
- 但**对照**：模型 `petal_0190_shell` 的 `quilt 70` 在 `solidify` **之后**再测仍正常返回 `boundary_closed=true`。所以不能简单归因为「模型含实体」，差异更可能与 `thicken` 消耗了 quilt 面有关，**根因未定位**。

**建议**：把异常包成与成功一致的结构化回执（`group.state + state_reason + status`），并给出 `contour_edge_visit_failed` 的触发条件与绕行建议；避免调用方拿到 tool-level error 而没有 `job_id` 之外的诊断。
