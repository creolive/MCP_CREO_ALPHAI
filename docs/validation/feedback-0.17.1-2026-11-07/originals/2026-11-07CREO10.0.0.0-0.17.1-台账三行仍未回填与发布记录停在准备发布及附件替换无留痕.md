### 2.1 一个重要更正：不要把工具层缓存当成仓库或 GitHub 的问题

本轮我先用网页抓取方式查询：

- `/releases/latest` 返回 `v0.17.0`（当时 `v0.17.1` 已发布约 30 分钟）
- `/releases?per_page=5` 返回 `v0.16.0 / v0.15.1 / v0.15.0 / v0.14.0 / v0.13.0`（缺 0.16.1、0.17.0、0.17.1）

改用 **`curl` 直连原始 JSON** 后，结果完全正确：

```text
1 v0.17.1 2026-11-07T01:58:29Z  draft=False pre=False assets=4
2 v0.17.0 2026-11-06T16:40:58Z  draft=False pre=False assets=4
3 v0.16.1 2026-11-06T14:03:23Z  draft=False pre=False assets=4
4 v0.16.0 2026-11-06T09:09:11Z  draft=False pre=False assets=4
...
count: 10
```

`/releases/latest` 用 curl 复查也返回 `v0.17.1`。因此本轮观察到的滞后**更可能来自抓取链路的缓存**，而非仓库或 GitHub API 缺陷。上一份反馈（0.16.0）把「列表缓存漏报」写成仓库风险，本次更正为：

- **不建议**把 `/releases?per_page=N` 当作「是否有新版本」的唯一依据；
- 但同样**不应据此认定仓库有问题** —— 判定前请用 `curl` 取原始响应或直接查 `/releases/tags/<tag>` 交叉确认。

对升级者的实际影响仍然存在：只信列表会**漏掉 0.16.1 与 0.17.1 两个 PATCH 版**。

## 6. 🟥 本轮新发现：已发布附件被替换，且对账文档记录值不可复现

### 6.1 事实链

| 时间 (UTC) | 事件 |
| --- | --- |
| 2026-11-06T09:09:08Z | `v0.16.0` 的 seed 包与两个 sidecar 上传（09:09:08~09） |
| 2026-11-06T09:09:11Z | `v0.16.0` 发布（`published_at`） |
| 2026-11-06T09:18:43Z | **`-source.zip` 与其 `.sha256` 才被创建/更新**（`updated_at` 09:18:45Z） |
| 2026-11-06T09:18:47Z | Release `updated_at` 随之更新 |
| 2026-11-07（本轮） | 用 curl 复查：0.16.0 source.zip 仍为 **8 096 403 B / `caa2cec0…`** |

即：**0.16.0 的同名源码包在发布后被替换过一次**（发布时 09:09，替换 09:18）。当前 body 里的 SHA256 与最终附件一致，所以**当前状态自洽**，但「已发布附件被覆盖」这一动作本身没有在 Release body、`RELEASE-0.16.0.md` 或任何 changelog 中留痕。

### 6.2 更具体的不一致：对账文档 vs 远端实际

`docs/development/DEV069-MAIN-RECONCILIATION-2026-11-06.md:14` 记录：

> 源码ZIP 8,106,399 B，API digest `2599964ac3c0713e7f1fc43fd61a4676500a2bbd55e2a71283e4b4909700b9e5`

而远端 `v0.16.0` 当前实际是：

> **8 096 403 B**，digest `caa2cec09f7cc217b1f5fc0fa3625d9a9f05cd46c3ecc6086c61ba4cff865ff9`

两者**大小相差 9 996 B、摘要完全不同**。该文档同一行还自述「本次附件内容校验：未下载 ZIP/sidecar 重算，不能把 API digest 当本次本地 SHA256 实算」。

结论：
- 0.16.0 源码包至少存在**两个不同内容**（`2599964a…` / 8 106 399 B 与 `caa2cec0…` / 8 096 403 B）；
- 对账文档记录的是**替换前**那一版，且明确未下载重算；
- 因此这份对账文档的附件证据**事后不可复核**，读者无法判断自己拿到的是哪一版。

### 6.3 建议

1. 已发布的 tag 与同名附件一旦上传即冻结；若必须替换，在 Release body 追加一行「assets replaced at <time>, previous SHA256 <hash>」。
2. 任何记录附件大小/摘要的文档，必须注明**取值方式**（API digest / 本地实算）与**取值时间**，并附可复现命令；只写 API digest 时不要与本地 SHA256 混称。
3. 发布流水线在**上传完成后**自动执行一次 `check_release_assets` 并把结果写入 `RELEASE-<version>.md`（与 §5.2 合并解决）。
