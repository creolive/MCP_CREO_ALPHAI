## 2. 🔴 核心问题：BUG-080 暴露"新接口验收缺单位维度"，且该缺陷对下游是静默 25.4 倍误差

### 2.1 事实链

- FEAT-045（`creo_inspect_session_assembly`）在 **0.5.0**（10-22）交付；
- 0.5.2 说明明确指出：**"0.5.1 及之前返回装配原单位的原始矩阵（英寸装配即英寸值）却声明毫米"**；
- 即：字段文档语义是毫米，实际值是装配原单位。在英寸装配里，客户端按毫米用会**差 25.4 倍**，
  且**没有任何报错或警告** —— 属于静默错误；
- 存活时长：0.5.0（10-22 12:13）→ 0.5.2（10-24 21:42），约 **2 天 2 个版本**；
- 发现途径：由**另一位用户**的 0.5.0 反馈（`2026-10-22_CREO10_v0.5.0_FEAT045交付与死锁根治但变换单位存疑.md`）指出，非本机发现。

### 2.2 修复本身是正确的（我做了静态核对）

`native/assembly_units.h` 的设计我认为是**教科书级的保守实现**：

```cpp
struct MillimeterScale {
    bool known = false;              // 未知不猜
    double scale = 1.0;
    ProError unit_query_code;        // 每个查询保留原始码
    ProError mm_unit_query_code;
    ProError conversion_query_code;
};
```
- 用真实 SDK 转换（`ProUnitInit` 取模型自身 mm 单位 → `ProUnitConversionCalculate`），不硬编码常数；
- `!isfinite || scale <= 0 || offset != 0` 一律判未知（注释明确"长度换算必须是有限正纯比例，offset 仅温度用"）；
- 注释写明教训："**never default unknown units to millimeters**，也绝不把未执行的查询报成 `PRO_TK_NO_ERROR`"；
- `transform_to_parent` 改为毫米归一化，原始矩阵保留在 `transform_to_parent_raw`（实现里 `transform_to_root_raw` 也有，比说明写的更完整）。

**结论：修复方向与实现都正确，无需返工。**

### 2.3 真正需要改的是"验收清单"

一个"声明单位与实际单位不一致"的缺陷，能在 0.5.0 通过 544 项单测 + 实机验收 + 三轮 WorkBuddy 黑盒，
说明**测试矩阵里没有"非毫米装配"这一维**：

- 实机验收用的是毫米装配 → 原单位 == 毫米 → 缺陷不可见；
- 只有英寸装配才暴露，而 `tools/test_assembly_units.py`（27 个单位/变换 case）是**发现之后才补的**。

### 2.4 建议（可制度化，成本很低）

1. **凡返回长度/坐标/变换/体积的新接口，验收矩阵强制包含"非毫米单位"一行**（英寸最典型）；
   与现有的"毫米装配"并列，作为最小必测集合；
2. 在 `docs/DEVELOPMENT.md` 或 `CODING_STANDARD.md` 里加一条硬规则：
   **"带单位语义的数值字段，必须同时返回单位名 + 换算系数 + 查询码，且未知时置 null 而非默认值"**
   —— 0.5.2 已经这么做了，把它写成规范就能防住下一次；
3. 把"单位"加入 WorkBuddy 黑盒提示词的固定场景项（当前黑盒是按功能列场景，缺"换一个单位再跑一遍"）。

### 2.5 ⚠️ 顺带提醒：这是一次静默的行为变更

`transform_to_parent` 的**数值口径**在 0.5.2 变了（原单位 → 毫米归一化）。
对**已经在 0.5.0/0.5.1 上"适应了错误数值"**的客户端，升级到 0.5.2 后同一装配的返回值会变化 25.4 倍。
建议在 README 显著位置（而非只在版本说明里）标注这一条 breaking change，
并明确"请改用 `transform_to_parent_raw` + `assembly.length_unit` 判定口径"的迁移写法。

## 3. 🟠 BUG-078：根因转为"会话级损坏"，但用户侧仍无自助路径

### 3.1 进展（正面）

`docs/work-items/BUG-078.md` 状态已从"已复现（0/4）"更新为：

```
状态：根因已定位（会话级损坏；代码序列无罪）；
      accept 两动作健康会话各 3/3 实机闭环；
      三个旧现场待操作者选择收尾（仅 restore_baseline 可用）
目标版本：待排期……"修复排期或不修"结论待台账/用户明确；
         按对照证据暂不安排延迟、重试或替换保存接口
```

这是实质进步：**证明代码无罪、健康会话可用**，也回应了我上轮"给排期或明确不修"的要求方向。

### 3.2 仍存在的问题

1. **结论仍悬空**："修复排期或不修"待明确。既然根因是会话状态损坏而非代码缺陷，
   那么"修代码"这条路本身可能不存在 —— 更需要的是**产品层面的处理策略**，而不是等排期。
2. **三个旧现场仍挂起**（`de6f0bb5…`/`bebe7e2b…`/`57294ff8…`），只能 `restore_baseline`（且要求现场=基线或 live 已缺失）。
   **用户手上没有一个"我这个会话是不是损坏了"的检测手段，也没有"怎么把它修好"的路径**。
   这正是我上轮建议的"补用户自助出路"，现在根因清楚了，这条建议可以更具体：
3. 建议（按根因重新设计）：
   - 给一个**只读的会话健康探针**（例如 `creo_session_status` 里加 `session_health` 字段，
     或独立工具），报告"备份动作是否可用"这类前置条件，让用户在建作业**之前**就知道会不会踩坑；
   - 给一条**面向损坏会话的恢复指引**（哪些操作能重建健康会话：重启 Creo？新建会话再打开模型？
     如何在保留原件的前提下放弃受管副本），写进 `docs/MODEL_RECOVERY.md`；
   - 明确告知"保护挂起"状态下用户**可以安全做什么、不可以做什么**（当前只有技术描述）。
