## 1. 用户需求（原始诉求）

> "我想要编辑（通过）MCP 打开的任意 CREO 装配体——还需要怎么修改 MCP？能实现吗？好实现吗？"

拆解为两个递进层次：

1. **结构级编辑**：对已打开的装配做元件增删/重摆/约束修改/元件尺寸修改；
2. **装配托管编辑**：装配像零件一样收养为托管副本（有 model_id、可 save/reconcile），编辑后可回存。

## 2. 现状：编辑能力卡在哪一环（基于实测）

MCP 的全部编辑工具（extrude/revolve/set_dimensions/component_constraints/assemble_component 等）**只作用于 MCP 托管模型**（凭 model_id）。当前链路在收养处断裂：

```
open_file（只读打开，v0.4.2 交付 ✅）
   → adopt_current_model（收养成托管副本）
        → 装配在此被拒："only part or sheetmetal models can be adopted"
   → 托管编辑工具
```

已具备的积木（七轮验收实测确认）：

| 积木 | 状态 | 版本 |
|---|---|---|
| 磁盘模型只读打开（.prt/.asm，含版本解析、幂等、审计） | ✅ | 0.4.2 |
| 会话清场（erase manifest + evidence + 装配先行排序） | ✅ | 0.4.6 |
| 装配打开结果回读组件清单（loaded_session_models） | ✅ | 0.4.6 |
| **零件**收养（inspect/prepare/apply，证据契约完整） | ✅ | 0.4.1+ |
| 新建装配（creo_new_assembly，公制模板） | ✅ | 早期 |
| 元件装配（assemble_component，fixed/default/constraints） | ✅ | 早期 |
| 约束（3 基准面对齐 + 20mm 偏置实测；mate/insert/csys 待验） | ⚠️ 部分 | — |
| **装配只读检查（组件树 + transform 提取）** | ❌ **唯一硬缺口** | FEAT-045 规划中 |
| 嵌套子装配装配 | ❌ | 文档明确 not supported yet |
| 装配收养 / reconcile 覆盖装配 | ❌ | 不支持 |
| 注册表条目治理（track_p01b 21.4MB 死锁） | ❌ | 三轮未解，见 v0.4.6 反馈 §4.1 |

## 3. 三条实现路线与难度评估

### 路线 A：结构级编辑（推荐优先，好实现）

**思路**：不收养装配本体，走"提取 → 重建"管线，全部使用既有工具：

```
open_file（装配，只读）
  → [FEAT-045] 读取组件树 + 每个 component 的完整 transform
  → 逐个 adopt 零件组件（现状已支持，毫米/无外部依赖的零件可过）
  → creo_new_assembly
  → assemble_component（按提取的 transform 摆放，或 constraints 精确约束）
  → 结构级编辑：remove_component / component_placement / 约束调整 /
    元件尺寸修改（编辑收养副本）
```

- **剩余工作量**：主要是 FEAT-045（只读组件树+transform 提取）+ transform 数值口径（Creo 4x4 矩阵 → assemble_component 的 XYZ mm + XYZ Euler 度的转换精度，建议提供 native 侧直读或给出转换公式与精度实测）。
- **难度：中等**。积木 80% 已存在且实测可用；FEAT-045 已在计划中。
- **限制**：嵌套子装配（assemble_component 暂不支持）与缺件装配（RETRIEVE_INCOMPLETE 场景）需在 FEAT-045 中一并定义行为（明确拒绝或降级报告）。

### 路线 B：装配整体收养（较难，建议分期）

**思路**：装配本体进入托管体系（有 model_id，可 save/reconcile）。

关键工程点：
1. **依赖物化**：装配天然违反现行"no external dependencies"契约。需复制装配+全部组件文件进 MCP 隔离区并重映射引用——姊妹项目 Solidworks_ClashMate_MechDog 的 `import_assembly`（复制 SLDSAM+依赖、虚拟件物化、完整核验后登记）已验证该模式可行，可直接参考其契约设计。
2. **前置条件——注册表治理必须先行**：track_p01b 一个零件的 model.json 已膨胀至 21.4MB 撑爆 16 MiB 预算且**死锁三轮未解**（adopt 与 reconcile 双双阻断，见 v0.4.6 反馈）。装配条目只会更大。若不做**条目分片/瘦身**（aliases/geometry 映射按 revision 分文件）就上装配收养，等于把唯一可用的 adopt 通道也堵死。
3. reconcile 扩展到装配（恢复/对账链路同步覆盖，避免"只进不出"单向门）。

- **难度：较难**。契约重构 + 存储治理 + 恢复链路三件事叠加，建议二期。

### 路线 C：原地编辑源文件（最容易实现，但不建议提出/实现）

ProMdlRetrieve 后直接修改并保存原文件，技术上最省事。但与全部既有安全契约冲突（"never saves, erases, renames or adopts"、证据绑定、recovery 纪律），源文件损坏/意外覆盖风险由用户承担。**本建议明确不推荐此路线**，仅列出以示完整。

## 4. 分期建议（按依赖关系排序）

| 期 | 内容 | 说明 |
|---|---|---|
| **一期（最高优先）** | **FEAT-045 落地**：只读外部装配检查——组件树（树序）、每组件 model_type/origin、完整 transform、缺失组件标记 | 路线 A 唯一硬缺口；同时让 `loaded_session_models` 从"名字清单"升级为"可重建的结构数据"。预算注意：transform 数据量远小于几何，不易触发 16 MiB 问题 |
| 一期并行 | **修复 track_p01b 死锁**：reconcile 免全量载入归档 + 预算错误结构化（对齐 adopt 诊断格式）+ 注册表条目分片/瘦身方案 | 死锁已三轮；也是二期装配收养的前置条件 |
| **二期** | 装配收养最小闭环：顶层装配物化（复制+重映射，参考 ClashMate import_assembly）+ 组件为已收养副本的组合装配；reconcile 覆盖装配 | 依赖一期并行项完成 |
| 二期可选 | "托管副本回存原盘"显式动作（用户明确确认后 save-as 到指定路径） | 覆盖"改完要落回原文件"的真实需求，且不破坏"never modify source"主契约（显式动作+显式确认） |
| 三期 | 嵌套子装配装配、mate/insert/csys 约束全谱系验证、装配图（drawing） | 现有 families 文档已标注这些为"待验证/不支持" |

## 5. 价值说明（为什么要做）

- **打通逆向工作流闭环**：用户的主线工作是 CAD 逆向复原（历史反馈中的键盘/液压缸实例均为此类）。当前"打开装配"只能看不能动，逆向分析到修改的最后一公里缺失。
- **存量装配是高频资产**：实测环境中的真实模型（asm_mx、hyd_cylinder_asm）均为存量装配；"只能从零建模"使 MCP 在存量场景价值受限。
- **投入产出比高**：路线 A 只差 FEAT-045 一块板；其余积木经七轮验收已验证可靠。

## 6. 一句话结论

**能实现。优先交付 FEAT-045（只读装配检查）即可用既有积木拼出"结构级编辑"完整管线（好实现）；装配整体收养建议在注册表治理完成后分期实施（较难）；原地改源文件不建议。**
