## 四、本轮问题明细

### P1｜官方源码包解压安装后，单元测试因 `git` 硬依赖报 13 处 ERROR

**复现命令**（在由 `MCP_CREO_MechDog-0.17.4-source.zip` 解压、无 `.git/` 的安装目录）：

```bash
.venv/Scripts/python.exe -m unittest tests.unit.test_t07_preview
```

**结果**：`Ran 235 tests … FAILED (errors=13)`；13 个 ERROR 全部为同一调用链：

```
tests/unit/test_t07_preview.py:27  from tools import test_t07_preview as driver
tests/unit/test_t07_preview.py:1325  self.acceptance = driver.Acceptance(...)
tools/test_t07_preview.py:340  "provenance": local_provenance()
tools/test_t07_preview.py:293  git("ls-files", "--", "*.py", "native/*.h", ...)
tools/test_t07_preview.py:282  subprocess.run(["git", ...], check=True, timeout=15)
=> CalledProcessError: 'git ls-files' returned non-zero exit status 128
=> fatal: not a git repository (or any of the parent directories): .git
```

**对照**：排除该模块后其余 **176 项 OK**（`tests.unit.test_release_download`、`test_native_planar_wall`、`test_release_assets`、`test_feedback016_receipts`、`test_sketch_solver_receipt`、`test_model_naming`、`test_job_query_protocol`、`test_rotation_admission`、`test_terminal_effect`、`test_dimension_guards`、`test_surface_measure_guard`、`tests.test_development_validation`）。因此 13 error 与产品功能无关，纯粹是**测试基建的环境假设**。

**为什么值得修**：

- 官方发布的交付物就是不含 `.git/` 的 `source.zip`（本包内只有 `.gitattributes` / `.gitignore` / `.github/`，无 git 元数据）。任何按「下载 ZIP → 解压 → 安装 → 跑测试」的用户都会遇到这 13 项。
- `tools/dev_check.py:254` 会调用 `tools/test_unit.py` 做全量门禁，而 Release body 宣称「组合源码全量单测 2762 项 0 失败 0 错误」。该结论只能在**开发者 git 工作树**下成立，与 `RELEASING.md` 第 5 步「从新目录解压并运行适用检查」的意图存在覆盖缺口。
- `BACKLOG.md` L355 的 `DEV-066` 已登记同类根因（「tools/ 离线证据工具硬依赖 PATH 中的 git：37 个脚本调用 git、32 处 `check=True` 无兜底」），状态仍是「待规划（仅登记，未实现）」。静态比对显示 `tools/test_t07_preview.py` 在 0.17.1→0.17.4 **逐字节未变**，`tests/unit/test_t07_preview.py` 只改了 3 行预览契约断言，因此这是**跨版未修的既有缺陷**，本轮首次从「官方源码包安装」路径实测到，不记为 0.17.4 新引入。

**建议**：`local_provenance()` 在 `git` 不可用或非工作树时降级为「按目录遍历收集文件名 + 标记 `git_unavailable`」，不要 `check=True` 直接抛；单元测试用可注入的 provenance 或 monkeypatch，使全量门禁在无 git 的分发包上也能跑通。`DEV-066` 可从「待规划」升级为发布门禁前置项。

> 说明：本机 `tools/test_unit.py` 全量运行历史上会因宿主删除守卫干扰挂起，故本轮**未复现 2762 项全量**，不宣称全量通过，也不据此断言作者门禁结论有误。

### P2｜发布后核对结论与新增逐 ID 核对表均未回填

- `RELEASE-0.17.4.md:44` 写「真实远端附件下载由**发布后** `check_release_assets.py --tag v0.17.4` 核对，mock 路线不等于真实网络」；§5 交付清单只写「本地四附件闸门…一致」。Release 已发布，但发布记录里没有回填远端核对结论。而 `RELEASING.md` 第 7 步明确要求「发布后用 … 核对远端恰有这四个附件…**核对结果写入发布记录**」，第 51 行新增的「发布后核验记录要求」也未落到具体记录。
- `RELEASING.md` 新增的「DEV-072：逐 ID 回填与发布后证据」规定「必须逐行填值，不能仅写『文档已同步』」，但其下 `L48–49` 的核对表**只有表头、0 行数据**；发布检查单模板 `L86–88` 的逐 ID 表同样全为空白占位符。本版至少涉及 `DEV-070` / `FEAT-007` / `FEAT-039` / `FEAT-058` / `DEV-072` 五个 ID，`RELEASE-0.17.4.md` 也没有等价的逐 ID 字面值记录。
- 也就是说：台账状态本身**已回填**（见 §三），但第 8 步要求的「逐 ID 字面值核对证据」与第 7 步的「远端核对结论」这两项**本版自身未闭环**——与 `DEV-062` 连续多轮「规范加了、执行漏了」是同一形态。

### P3｜主台账计数口径易误读

实算 `docs/BACKLOG.md` 表格：**186 行 / 186 个唯一 ID，无重复**。`L123` 的「台账 185→186 行 / 186 唯一 ID」正确，并说明「上方分类表保留 0.17.2 前历史口径，未随 0.16.1—0.17.4 逐版重算」。但：

- `L125` 首句「**共 178 项**：176 项工作记录、2 项历史观察；…**178 行对应 178 个唯一 ID，无重复**」使用现在时，与 186 冲突（其后才是各轮历史统计说明）。
- `L112–122` 分类表合计 `6+25+10+0+31+49+3+58+0+0 = 182`，与 186、178 均不同。

建议在 `L125` 首句前加「以下为 2026-11-03 历史时点统计」之类的显式时点标记，或把当前结论统一为 186 行；否则按 ID 核对的读者无法判断哪个数字是现行口径。

### P3｜API 回退仍绑定 `github.com` 下载域名

`src/creo_mechdog/release_download.py:63–80` 在 API 回退里取 `browser_download_url`，并硬校验 `parsed.netloc == "github.com"`、路径为 `/<repo>/releases/download/<tag>/<name>`，然后 `urlopen` 该地址。安全性校验本身合理，但本机历史曾出现 **`github.com` 直连 `curl(28)/(52)` 失败而 `api.github.com` 正常**的环境；此时即使 API 元数据获取成功，四个附件仍下载不了，`--tag` 会整体失败并退回人工 `--dir`。本次实测 `github.com` 可达，故不记为当前失败。

建议增加二级回退：`https://api.github.com/repos/<repo>/releases/assets/<asset-id>` + `Accept: application/octet-stream`（本报告方升级流程一直使用这条路线），并在记录中说明采用了哪条下载通道。
