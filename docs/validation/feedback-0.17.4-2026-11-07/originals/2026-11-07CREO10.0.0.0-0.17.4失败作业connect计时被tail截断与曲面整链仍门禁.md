## 4. 本轮发现的问题

### 4.1 【P1 · 新】失败作业的 `connect` 阶段计时被 tail 窗口截断，`native_progress` 仍报 `no_stage_timing`

**这是 0.13.0 反馈 `connect idle_seconds=null` → 0.15.0 `BUG-109` 修复的残留缺口。**

`0.15.0` 声明：原生在 `connect_creo` 前后各发一条带 `ts`/`elapsed_ms` 的 `STAGE`，`native_stage.stall_report` 可把会话附着耗时与首个操作阶段分开。0.17.4 的 `native.log` 确实有这两行，**但 `stall_report` 读不到**：

```
jobs/25c44c7fdb864dfe9d9c0566741efe96/native.log   总长 8469 B
TAIL_BYTES = 8192  → 只读 [277, 8469)
byte 15 : STAGE name=connect   elapsed_ms=64   since_start_ms=64   ts=1794032408109
byte 110: STAGE name=connected elapsed_ms=4723 since_start_ms=4787 ts=1794032412833
```

两条 STAGE 都在 277 B 之前，被整体截掉。该失败作业的公开回执因此是：

```json
"native_progress": {"readable": true, "log_bytes": 8469, "tail_bytes": 8192,
  "truncated": true, "stage": "result_delivery_complete", "sub_stage": null,
  "elapsed_ms": null, "since_start_ms": null, "idle_seconds": null,
  "stages_seen": 0, "reason": "no_stage_timing"}
```

而同一作业 `result.verify_stages` 里却有 `connect elapsed_ms=64`、`connected elapsed_ms=4723`（来自另一条终态路径）。**同一份结果里，一个说有阶段计时，一个说没有。**

**根因**（`src/creo_mechdog/native_stage.py:28` `TAIL_BYTES=8192`、`:109` `_read_tail`）：`stall_report` 只解析末尾窗口内的 `STAGE` 行；`connect`/`connected` 天然写在日志最开头，一旦日志因失败诊断（例如 `edge_geometry` 候选清单）超过 8192 B 就必然丢失。成功作业因为末尾还有十几条 `verify_model_*` STAGE 而"看起来正常"，**恰恰失败/挂起作业最需要这段计时，却最常看不到**。

**影响**：
- 0.13.0 反馈的原始症状（`idle_seconds=null`、`reason=no_stage_timing`）在 0.17.4 的失败作业上**逐字复现**；
- 黑盒用户无法区分"卡在 Creo 会话附着（4.7 s）"与"卡在建模/回滚"，`stall_report` 这个能力名存实亡；
- `stage`/`sub_stage` 与 `result.verify_stages` 口径冲突，容易被误读成数据错误。

**建议**（任选其一，成本都很低）：
1. `stall_report` 对 `STAGE name=connect|connected` 额外扫描**日志头部**固定 4 KiB，与 tail 结果合并去重（推荐，改动最小、仍保持有界读取）；
2. 或把 `connect` 阶段的 `ts`/`elapsed_ms` 同时写进 `native_result.json` 的结构化字段，由 Python 侧直接投影，不依赖 log 文本解析；
3. 或在 `native_progress` 里显式标注 `connect_stage_outside_tail=true` 与 `head_bytes_scanned`，至少避免把"没读到"误报成"没有计时"；并统一 `stage`/`sub_stage` 与 `verify_stages` 的命名口径。

**复现**：在任意有 ≥1 条折边/草图的模型上提交一条 `edge_geometry` 近失配折边（见 §3 的端点），作业会因诊断文案使 log 超过 8 KiB，即可稳定得到上述 `native_progress`。

### 4.2 【P2 · 新】`skipped_no_geometry` 仍返回一个不存在的 `preview.path`

`e62f19949d33459487dddb90d97376ce`（空模型）回执：

```json
"preview_file": null,
"preview_status": "skipped_no_geometry",
"preview": {"status": "skipped_no_geometry",
            "path": "E:\\…\\jobs\\e62f1994…\\output\\preview.jpg",
            "bytes": -1, "file_verified": false, "file_check": null, "codes": {…全 null…}}
```

实测 `jobs/e62f1994…/output/` **是空目录，没有 preview.jpg**。源码 `native/preview.h:537` 在 `skipped_no_geometry` 分支只把 `codes` 和 `failed_code` 置空，`{"path", outcome.path}` 仍原样输出；`src/creo_mechdog/preview.py:127` 也只把 `file_verified/size` 置空，没有清 `path`。

**影响**：黑盒调用方按 `result.preview.path` 去读图会得到缺文件；顶层 `preview_file=null` 与 `preview.path` 非 null 自相矛盾。功能判定本身是对的（§3 已确认），只是回执清理不彻底。

**建议**：`skipped_no_geometry` 时把 `preview.path` 置 `null`（或改名为 `intended_path` 并附 `exists=false`），让"状态=跳过"与"路径=null"一致；`bytes=-1` 建议改 `null`，避免被当成真实字节数。
