## 4. 本轮发现的问题

### P0-1 `creo_surface_loft` 在 Creo 10 SDK 上是「必败工具」：编译期被屏蔽，运行期报错，但能力清单仍标 `enabled=true`

作业 `a1490ab371824c57a8810ea3d9d92e46`，两个合规的圆形截面（`sec_bot` R20 / `sec_top` R10，同一 XY 平面族、相距 16）：

```text
status = failed, stage = execute_surface_loft, toolkit_code = -1
message: "surface_loft requires Probbl.h, which this Creo Toolkit SDK does not ship;
          the boundary-blend element tree is unavailable on this SDK generation"
rollback_succeeded = true, revision 2 → 2（无副作用）
```

根因在两处，且都在本机可验证：

1. **头文件缺失**：`D:/Program Files/PTC/Creo 10.0.0.0/Common Files/protoolkit/includes/Probbl.h` → `No such file or directory`。`native/surface_loft.cpp` 现有 `#if __has_include(<Probbl.h>)` 守卫（带 `LOCAL PATCH (Creo 10 SDK)` 注释），因此**整个函数体被编译掉**，运行时只能返回「不可用」。
2. **枚举值缺失**：`PRO_E_DTM_SRF_TYPE_BND_BLEND` 在 `creo_lookup_constants` 查不到；对 Creo 10 全头文件 `grep -rn "BND_BLEND\|BLEND_SRF"` → **零命中**。即这个 SDK 代际根本没有「基准曲面=边界混合」的子类型定义。

**但真正关键的是：这套树并不需要 Probbl.h 才能编译。** 实测常数：

```text
PRO_FEAT_DATUM_SURF = 942            ✅ 存在于 ProFeatType.h
PRO_E_DTM_SRF_TYPE  = 1131           ✅ 存在于 ProElemId.h
PRO_E_BNBLN_CURVES  = 661            ✅ 存在于 ProElemId.h
PRO_E_BNBLN_1DIR    = 651            ✅
PRO_E_BNBLN_DIR_CURVES = 657         ✅
PRO_E_BNBLN_RULED   = 1206           ✅
（ProElemId.h 共 34 个 PRO_E_BNBLN_* 定义，creo_lookup_constants 全部可查）
```

缺的只有 `PRO_E_DTM_SRF_TYPE_BND_BLEND` 这一个**取值**。

**建议**：
1. `capabilities.families.surface_loft` 在编译期判定 SDK 缺头时，`enabled` 应置 `false` 并给出 `unavailable_reason: "sdk_header_missing: Probbl.h"` 与 `creo_release_numeric`；现在标 `enabled=true / tool=creo_surface_loft`，上层会排进计划、白烧一个作业。
2. 把 `PRO_E_DTM_SRF_TYPE_BND_BLEND` 的取值内联为常量（不必从 Probbl.h 取），并在 `#if` 分支里保留手写树路径 —— 这样 Creo 10 有机会真正跑通，而不是把整个算子编译掉。
3. 能力清单增加 `sdk_requirements` 字段（如 `["Probbl.h"]`），让调用方在选择「全程曲面法」路线前就能预判。

### P0-2 第 4 步修剪的失败诊断不足：真正原因是「开放带面与球面的交线是开放弧，不能分割 quilt」，报错只说「确认工具确实相交」

两次修剪都失败：

| 作业 | 工具 | 结果 |
| --- | --- | --- |
| `0b66402e422746c1baf8fb1aa001f8e8` | `quilt 195` = 任务书口径 50° 锥面带（z −33→−17，r 31→28） | `feature_status=6`, `feature_id=314`, `target_quilt_id=82`, `keep_side=one`，面积前后同为 27576.9003 |
| `dfa288eeed6143a48d03f844819efa8d` | `q_petex` = 同一锥面**延长到 z=−10**（r 31→26.5），排除「工具太短」假设 | 同样 `feature_status=6`, `feature_id=350` |

报错文案完全相同：

```text
Surface trim regeneration failed (feature_status=6, feature_id=…, target_quilt_id=82,
tool=quilt, keep_side=one); check that the tool actually intersects the target quilt
```

**我用解析几何核对了这两次失败，不是「没相交」，而是「相交成一条开放弧」**：

```text
锥面  r_c(z) = 31 − 0.1875·(z + 33)
球面  r_s(z) = sqrt(1089 − z²)
z=−18: r_c=28.1875, r_s=27.6592  → 锥面在外
z=−17: r_c=28.0000, r_s=28.2843  → 锥面在内
交点 ≈ z=−17.3 —— 恰好贴在工具带上边界 z=−17 附近
```

工具是**只有 50° 宽的开放带**，它和球面的交线是一条**开放弧**；Creo 修剪要求工具在目标面上形成**能分割曲面的闭环**，开放弧做不到 → `feature_status=6`。把工具延长到 z=−10 后交线仍在带内成开放弧，所以依然失败。

**这解释了两轮（0.17.4 / 0.18.2 / 0.18.4）反复卡在第 4 步的真正机理**，也解释了为什么上一轮「先 ProMerge 合成单一 quilt 再修剪」救不了：问题不在 quilt 组织，而在**工具是否闭合成环**。

**建议**：
1. 失败回执增加交线几何诊断：`intersection_curve_count`、`closed_loop_count`、`curve_length_mm`、`touches_tool_boundary`（布尔）、`segments_on_target`。这样上层能一次判断「是没相交 / 相交成开放弧 / 相交成闭环」。
2. 提供 `surface_trim(tool_mode="extend_to_loop")` 之类选项，或明确文档写「开放工具带不能修剪，需先把爪的四壁缝成闭合环」。
3. `capabilities.surface_chain.limits` 目前没写这条拓扑约束，建议补上。

### P1-1 `creo_measure_surface_group` 在真实组上两处判据不可用，且 `state_reason` 与自身字段矛盾

作业 `d027a3cc56fb4d1c885bae1fd1ac144e`（对 4 面 / 27 576.9003 mm² 的真实桶面组）：

```json
"state": "open",
"state_reason": "boundary_edges_unavailable",       // ← 与下面矛盾
"boundary_edges": 10,
"open_edges_status": {"available": true, "boundary_edges": 10, "joined_edges": 8,
                      "topologically_shared_edges": 8, "query_code": 0},
"gap_max_mm": null,
"gap_max_status": {"available": false, "reason": "no_member_seam_candidate"},
"overlap_area_mm2": null,
"overlap_status": {"available": false, "reason": "overlap_sample_budget_exceeded",
                   "query_code": -1}
```

两点问题：

1. **`state_reason` 自相矛盾**：`boundary_edges` 明明有值（10）且 `open_edges_status.available=true`，`state_reason` 却说 `boundary_edges_unavailable`。上层按 `state_reason` 判断会误以为「无法测边界」，实际是「边界测得 2 条开口边」。
2. **`overlap` 在真实规模上直接不可用**：`overlap_sample_budget_exceeded`（`query_code=-1`）。作者 H04 的证据是 800 mm² 级小面；到 27 576 mm² / 4 面组时就超采样预算，而第 7 步「缝合时不得重叠」正是需要它在大面上工作的场景。

正面：`gap_max` 为 null + `reason=no_member_seam_candidate` 是**正确行为**（两片已拓扑共边 8 条，没有缝可测），这条设计我认可。

**建议**：修 `state_reason` 取值逻辑（有 `open_edges` 时应给 `open_edges_present`）；`overlap` 预算随面积自适应，或返回「已测面片对 / 总面积 / 建议 tolerance」让上层降级判断。

### P1-2 `kept_quilt_visit_code=-4` 仍在：H06 只补了判据字段，下游 quilt 引用依然不可用

同一次成功的修剪（作业 `ef978ca5…`）：
