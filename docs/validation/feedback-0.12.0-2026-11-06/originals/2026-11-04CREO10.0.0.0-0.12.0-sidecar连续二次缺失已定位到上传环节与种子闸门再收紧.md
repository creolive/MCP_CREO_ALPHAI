## 1. 唯一问题（第二次提出）：`.sha256` sidecar 又缺了 —— 这次可以把根因钉到"上传环节"

### 现象

`v0.12.0` Release assets 与 0.11.7 相同，只有 2 个 ZIP、**没有 `.sha256` sidecar**。对照：0.4.4–0.11.5 连续多版有（DEV-045 固化），**0.11.7、0.12.0 连续两次缺失**。

### 本轮新增的定位（比上次更精确，可直接修）

昨晚报告只说了"建议并进 package.py"。本轮读码发现**生成环节根本不缺**：

```python
# tools/package.py:126 —— 本地生成 sidecar 是存在的
archive.with_suffix(".zip.sha256").write_text(f"{checksum}  {archive.name}\n", encoding="ascii")
```

也就是说：`package.py --output` 在本地已经**产出了两个 `.zip.sha256` 文件**，0.11.7/0.12.0 发布时**只是没把它们上传到 Release**。缺口不在构建，在 **Release 上传清单**。

而 `docs/development/RELEASING.md` 现状是：
- 第 7 步只要求"Release body 必须直接列出文件名及完整 SHA256"（body 这次也没缺）；
- 第 9 步是相对上一正式包的身份核对；
- **没有任何一步核对"Release assets 数量 = 4（两个 ZIP + 两个 sidecar）"**。

`package.py --seed-archive` 闸门（0.10.1 P04）证明了"把检查做进脚本"在这条流水线上是有效的——同一思路补上最后一块即可。

### 建议（两选一，均一行级成本）

1. **首选**：把 sidecar 上传并进发布脚本/流程——`package.py` 顺手在输出末尾打印 `upload: <zip> <zip.sha256> <seed.zip> <seed.zip.sha256>` 四件清单；或
2. `RELEASING.md` 第 7 步加一句硬核对："**Release assets 必须为 4 个文件（两 ZIP + 两 sidecar），数量不为 4 视为未完成交付**"。

连续两次（0.11.7、0.12.0）说明这不是偶发遗忘，而是流程缺口。两个 ZIP 的哈希 body 里都有，升级者目前仍可核对，所以**严重性低**；但 sidecar 对脚本化下载方（`curl xxx.sha256` 拿期望值的模式）是承诺过的接口，连续缺失会让自动化方退回"解析 body"的脆弱路径。

### 好消息：0.12.0 把种子闸门又收紧了一档（DEV-061）

`RELEASING.md` 第 5 步现在的顺序是强制性的：**先 `package_seeds.py --output` 确定性构建 → 实测 SHA256 显式回填 `docs/seed_package.json` → 重建一次确认哈希不变 → 再 `package.py --seed-archive` 制作源码包**。且 `package_seeds.py` 构包后**默认校验**受信记录（未回填/版本不符即非零退出，`--allow-record-mismatch` 不得用于发布）；`tests/unit/test_seed_record_gate.py` 在单元阶段守同一件事；`package.py` 在"缺参、摘要不符、版本不符、两份清单不一致、**README 当前版本段滞后**"五种情况下都在写出任何源码包之前失败。

—— README 版本段滞后（0.9.0 那次）、种子摘要脱节（0.8.1/0.9.0 那两次）、清单版本不一致（BUG-089）四类事故现在**全部有脚本闸门**。这套东西走到今天的状态，值得在下一个 MINOR 的版本说明里正式肯定一次。
