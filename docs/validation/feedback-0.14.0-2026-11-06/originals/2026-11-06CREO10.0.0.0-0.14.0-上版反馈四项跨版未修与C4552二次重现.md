## 4. 本版发现的问题

### 4.1 【P1，跨版未修 + 二次重现】`native/surfaces.cpp(168)` C4552：`ProQuiltInit` 错误码仍被丢弃

0.14.0 在本机 Creo 10 SDK 编译日志中**原样重现**：

```
E:\...\native\surfaces.cpp(168): warning C4552: '!': 未使用表达式的结果
```

源码（`generic_surface_offset`，0.13.0 新增 `creo_surface_offset` 的源面积测量路径）与 0.13.0 **逐字节相同**：

```cpp
ProQuilt quilt = nullptr;
if (!ProQuiltInit((ProSolid)board, quilt_id, &quilt); quilt) {   // ← 168
    MeasurementOutcome area = quilt_area_native(quilt);
    ...
}
```

这是 C++17 `if (init; condition)`；`init` 里的 `!ProQuiltInit(...)` 布尔结果被丢弃，实际条件只剩 `quilt != nullptr`，`ProError` 返回码**从未被检查**。若初始化失败而 `quilt` 非空，仍会测量无效面组，污染本版对外承诺的 `measured_offset_distance_mm = 体积 ÷ 源面积`。

**跨版证据**：`native/surfaces.cpp` 不在 0.13.0→0.14.0 的 28 个真实改动文件里；全仓 `!ProQuiltInit` 仍只有 3 处，`quilt_merge.cpp:63/67` 是正常的 `if (!ProQuiltInit(...))` 条件判断，只有 168 行受影响；编译警告计数从 0.13.0 的 1 条到 0.14.0 的 1 条，位置不变。

**建议**（与上版相同，恳请优先处理）：

```cpp
if (ProError st = ProQuiltInit((ProSolid)board, quilt_id, &quilt);
    st == PRO_TK_NO_ERROR && quilt) { ... }
```

并把 C4552 纳入发布编译日志扫描（例如 `dev_check.py` 增加「编译日志出现 C4552 即失败」），避免「表达式被丢弃」静默进入发布包。

> 本项仅由编译警告 + 源码静态分析得出，**未做 Creo 实机复现**（§1 冻结），不宣称已观察到错误面积或错误返回值。

### 4.4 【P3，跨版未修】sidecar 仍为 CRLF，标准 `sha256sum -c` 仍失败

字节级复验（0.14.0 官方附件）：

```
source.zip.sha256      102 B  CRLF=True  CR=1 LF=1
seed-library.zip.sha256 108 B  CRLF=True  CR=1 LF=1
$ sha256sum -c MCP_CREO_MechDog-0.14.0-source.zip.sha256
sha256sum: 'MCP_CREO_MechDog-0.14.0-source.zip'$'\r': No such file or directory
MCP_CREO_MechDog-0.14.0-source.zip: FAILED open or read
```

根因仍在 `tools/package.py`：`sidecar.write_text(f"{checksum}  {archive.name}\n", encoding="ascii")` 未指定 `newline="\n"`，Windows 文本模式把 `\n` 写成 `\r\n`（`newline=` 在包内计数仍为 0）。`check_release_assets.py` 用 `splitlines()+strip()` 能容忍，但按标准 `sha256sum` 校验的升级者会直接失败。建议固定 LF（`write_bytes` 或 `newline="\n"`），并在 `INSTALL.md` 补 `tr -d '\r'` 兼容写法。

### 4.5 【P2，新增】反馈归档积压扩大到三批

0.13.0 包已归档 `feedback-0.11.5-*` 与 `feedback-0.11.7-*`；0.14.0 包内检索 `feedback-0.12.0-*` / `feedback-0.12.1-*` / `feedback-0.13.0-*` **均为 0 个文件**。也就是说 0.12.0、0.12.1、0.13.0 三批反馈（含本文件所回应的上一版报告）尚未进入 `docs/validation/feedback-*` 的 `MAPPING.md` + `manifest.json` + `originals/` 流程。既然机制已建立，建议按批次补齐，避免反馈与台账脱节。

### 4.6 【观察项，非项目缺陷】版本语义与版本发现延迟

- 0.14.0 的 Release body / `RELEASE_NOTES_0.14.0.md` / `BACKLOG.md` 均自称「**PATCH 性质**」，但版本号由 0.13.0 跳到 **0.14.0**（SemVer MINOR 位）。本版新增 `extrude_depth` 7 键回执属向后兼容功能扩展，按 SemVer 用 MINOR 是合理的，建议统一措辞（例如「小范围 MINOR」）以免升级者误判变更范围。
- 本轮 11:34 的一次查询中，`/releases?per_page=5` 与 `/commits/main` 仍返回 0.13.0 / `d90d28e…`；11:54 再查才返回 0.14.0 / `c774fa26…`，而 Release `published_at` 是 `02:22Z`（北京时间 10:22）。**疑为 GitHub API 列表缓存/排序延迟**。这不是仓库缺陷，但建议升级者不要只依赖列表接口：用 `/releases/tags/<tag>` 与 `/commits/main` 交叉确认，避免把「已发布」误判为「无新版本」。
