## 2. 🔴 核心问题 1：参数校验错误倾倒整个 pydantic 联合类型

### 2.1 现象

三个完全不同的入口，只要参数校验失败，报错**第一行**就是同一个 `list[tagged-union[...]]`，把 `FeatureGroupOp`、`ReorderOp`、…、`RibOp` 等 **60 余个**操作类型名（含 `function-after[...]` 校验器签名）全部打印出来，随后才是一行真正有用的信息。

**入口 A —— 只读工具 `creo_get_mass_properties`，传负密度：**

```text
Error executing tool creo_get_mass_properties: 1 validation error for
list[tagged-union[FeatureGroupOp,function-after[one_position(), ReorderOp],
  function-after[nonzero_angle(), AxisPatternOp], ... ,RibOp]]
0.mass_properties.density_g_cm3
  Input should be greater than 0 [type=greater_than, input_value=-1.0, input_type=float]
    For further information visit https://errors.pydantic.dev/2.13/v/greater_than
```

`density_g_cm3=0` 报同样的整包前缀。

**入口 B —— 独立工具 `creo_hole`，thread_depth 超表上限：**

```text
... list[tagged-union[...60+ 类型名...]] ...
0.hole
  Value error, thread depth 20.0 mm exceeds the ISO M6 table limit of 12.0 mm
  [type=value_error, input_value={'op':'hole','label':'...'}, input_type=dict]
```

**入口 C —— `creo_hole` 表外尺寸 `M7`**：同样整包前缀，有效信息只有
`standard hole size 'M7' is not in ISO iso_metric_coarse@1; frozen sizes: M10, M12, M3, M4, M5, M6, M8`。

### 2.2 影响

- 有效诊断（"密度必须 > 0" / "超出表上限"）被**数千字符的类型名淹没**，客户端日志、UI 提示和反馈文档都难以直接阅读。
- 路径写成 `0.mass_properties.density_g_cm3` / `0.hole`，暴露了"只读工具也被包装成 `operations[0]` 走同一套 plan 校验器"的内部实现；调用方看到 `list[...]` 会误以为自己传错了一整个计划。
- `input_value` 会回显**整个操作 dict**（含 label、引用、offset 等），存在把模型业务数据带进错误日志的隐患。
- 与同版本的 `creo_plan_product_variant`（一句 `parameters.wall_mm: outside declared bounds`）形成鲜明对比，说明这不是框架限制，而是错误映射缺失。

### 2.3 建议

1. 在工具层捕获 `pydantic.ValidationError`，只投影 `loc[-2:]` + `msg` + `input_value` 的标量值，例如：
   `creo_get_mass_properties: density_g_cm3 must be > 0 (got -1.0)`。
2. 不要回显整个 operation dict；只回显出错字段的值。
3. 把 `0.<op>` 前缀映射回真实工具参数名。

## 3. 🔴 核心问题 2：质量属性对装配静默按均质计算 + 单位字段矛盾

### 3.1 工具声明"装配会被拒绝"，实机却返回了质量

工具描述原文：

> Parts only: assemblies are refused until their own query path is verified.

0.18.0 版本说明也写：「质量属性只支持受管零件；装配/钣金的多实体与 occurrence 汇总、材料密度来源与单位契约仍开放」。

实测（同一 Creo 10 会话）：

| 模型 | `volume_mm3` | `mass_unit` | `query_codes.mass` | `material_assigned` |
| --- | --- | --- | --- | --- |
| 空装配 `39eeea…` | `0.0` | `null` | `null` | `false` |
| out4 双组件装配 `2deff0…` | `149231.8444` | `null` | `null` | `false` |
| 钣金件 `4c38b0…` | `7835.6195` | `"tonne"` | `-1` | `true` |
| 实心块 `128aa0…` | `239793.8189` | `"tonne"` | `-1` | `true` |

装配体积 `149231.8444` 与 `out4` 报告中独立实测值一致，重心 `[-19.944, -4.186, 61.135]` 也合理 —— **几何本身是对的**。但对装配传 `density_g_cm3=7.85` 后，返回：

```json
{"volume_mm3":149231.84440013696,"mass_g":1171.469978541075,
 "density_source":"request","material_assigned":false,
 "mass_unit":null,"query_codes":{"volume":0,"mass":null,"units":null}}
```

`1171.4699 = 149231.8444 × 7.85 / 1000`，即**把整个多组件装配当作单一均质材料算出了质量**，而回执里没有任何 `composition` / `component_count` / `mass_source` 说明这是假设值；`query_codes.mass=null`、`mass_unit=null` 表明原生质量属性根本没查到。这与工具描述"装配会被拒绝"直接冲突，且比"拒绝"更危险：产出一个**看似合法、实则无依据**的数值。

### 3.2 `mass_g` 与 `mass_unit` 自相矛盾

对钣金件 `4c38b0…` 传 `density_g_cm3=7.85`：

```json
{"volume_mm3":7835.61946843261,"mass_g":61.50961282719599,
 "density_g_cm3":7.85,"density_source":"request",
 "mass_unit":"tonne","query_codes":{"volume":0,"mass":-1,"units":0}}
```

`mass_g=61.51` 是**克**（7.835619 cm³ × 7.85 g/cm³ = 61.51 g，与 `mass_properties.py` 中 `expected = volume * density / 1000` 一致），但 `mass_unit` 同时报 `"tonne"`。按字段名读会得到 61.51 g，按 `mass_unit` 读会得到 61.51 吨，**相差 10⁶ 倍**。根因是 `mass_unit` 直接透传了 Creo 原生质量单位名，而 `mass_g` 是 Python 侧换算后的克值，两者被放在同一回执里却没区分。

### 3.3 `query_codes.mass=-1` 时质量是计算值，却未标注来源

所有 Creo 10 受管零件都出现 `material_assigned:true` 但 `query_codes.mass=-1`、`mass_g:null`（不给密度时）——说明本机原生密度/质量查询读不到，作者声明「材料密度来源与单位契约仍开放」在此得到证实。传密度后 `mass_g` 由 Python 侧算出，但回执只有 `density_source:"request"`，**没有 `mass_source:"computed_from_density"`**，调用方可能误以为是 Creo 原生质量属性读数。

### 3.4 建议

1. 按文档真正拒绝装配；若要开放，则回执加 `model_type`、`component_count`、`composition`，并在 `mass_g` 旁明确标注 `mass_source` 与 `assumption:"homogeneous"`。
2. 把 `mass_unit` 改名 `native_mass_unit`，并新增权威的 `mass_value_unit`（固定 `"g"`）；或直接让 `mass_unit` 与 `mass_g` 同单位。
3. 新增 `mass_source: "native" | "computed_from_density" | "none"`，与 `density_source` 配对；`query_codes.mass=-1` 时禁止把计算值伪装成原生读数。
4. 补充 Creo 10 上「`material_assigned=true` 却读不到密度」的诊断（是材料无密度，还是 Toolkit 查询不支持）。

> 正面：数值守卫生效（负密度、0 密度被拒），无密度时 `mass_g=null` + `hint` 而不伪造值，这一设计是对的。

## 5. 次要问题

### 5.1 🟡 标准螺纹孔 `depth_basis` 无法从元素树确认

成功回执里：

```json
"depth_basis": "not_tip", "depth_scheme_code": -1,
"depth_scheme_query": "PRO_E_HLE_DEPTH_DIM_TYPE"
```

`hole_standards.py` 用 `DRILL_TIP_ANGLE_DEG=118` 和 `tip_cone_height_mm()` 来把 `thread_depth` 限制在真实钻尖深度内，但原生深度方案查询返回 `-1`，回执只能标 `not_tip`。本例几何（206.18 mm³）与「到肩 10 mm + 钻尖锥」吻合，但缺少元素树级确认。建议在 Creo 10 上补一次 `PRO_E_HLE_DEPTH_DIM_TYPE` 读回，或把 `depth_scheme_code=-1` 明确标注为"未知，按几何推断"。

### 5.2 🟡 只读工具返回 `job_id`

`creo_get_mass_properties` 每次都返回 `job_id`（如 `0092841d…`），revision 不变、不产生模型变更，语义上仍是只读，但会让调用方误以为要轮询 `creo_get_job`。建议文档说明该字段只是执行记录标识，或改为 `request_id`。

### 5.3 🟡 规划器只有一个模板

`box_frame` 是唯一模板；`template_id` 传其他值的行为未在本轮测试。若定位是"离线规划能力族"，建议给出模板清单与扩展契约（当前 `capabilities` 的 `seeds` / `families` 段未列模板目录）。

1. 🔴 **修参数校验错误映射**（§2）——影响 0.18.0 全部工具的可用性，改动小、收益最大。
