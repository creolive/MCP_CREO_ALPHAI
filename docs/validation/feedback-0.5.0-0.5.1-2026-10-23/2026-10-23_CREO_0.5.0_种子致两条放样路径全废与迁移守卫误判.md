## 三、BUG-036（装配约束位姿）：读侧已修，写侧在 Creo 9 依旧

**背景**：我自 0.3.2 起连续 6 轮报告"`component_constraints` 应用约束后元件位置不重新求解"。0.4.3 的修复说明是"native 组件变换读取重写……位姿查询修复已回归，**实机几何验证与外部 Creo 9 复验仍按卡保留**"。本机正是缺失的 Creo 9 复验环境。

**实测**（wb_acc_asm，元件 c1 原放置 (-30,20,0)+绕 Z 30°，施加 mate+align+align 于三正交基准面、零偏移）：

| 步骤 | transform_to_parent |
|---|---|
| 施加约束后 | 平移 `(-30, 20, 0)`，旋转 cos30°/sin30°（**旧放置**） |
| `creo_regenerate` 成功后 | 平移 `(-30, 20, 0)`，旋转 cos30°/sin30°（**仍旧放置**） |

约束的几何要求是元件基准面与装配基准面重合（零偏移、黄/黄）→ 期望变换应为**单位矩阵**；实际位姿 30° 旋转下法向完全不可能满足 mate/align。即：**装配被留在了违反新约束的状态，而 `component_constraints` 返回 succeeded、`underconstrained: false`，无任何不一致提示。**

**评价**：0.4.3 的"读侧诚实化"是真的有用——现在 `creo_inspect_session_assembly` 报出的变换与真实位姿一致，调用方至少能**发现**不一致。但核心问题（约束应用后位姿不重解、regenerate 也不重解）在 Creo 9 上原样存在。

**建议**：
1. 在 `component_constraints` 成功后增加**一致性自检**：用新约束求解期望位姿并与实际变换比对，不一致时在结果中以 `placement_matches_constraints: false` + 原因明示（而非仅 succeeded）；
2. 排查正确的重解调用序列（`ProAsmcompConstraintsSet` 之后显式更新放置/装配再生），使 Creo 9/12 行为一致；
3. 若短期无法重解，至少在工具描述与返回中注明"约束已设置，位姿需在 Creo 中再生/移动后更新"。

## 五、P1 新问题：`creo_migrate_registry` owner 守卫在 MCP 路径误判

**现象**：`creo_migrate_registry(mode=apply)` 连续两次被拒：

```
Registry migration cannot rewrite an active or unproven job
holder: {job_id: ba0901e5…, model_id: 701981d4…(wb_reg_pat2), operation: registry_owner}
```

**但被引用的作业是终态**：`status: succeeded`（10-16 06:37 完成）、模型 `ready`、`pending_job/recovery_pending` 均为 null。我用**同一函数、同一参数**从本地进程调用：`_check_owners` **通过**，且完整 apply 成功（`migrated: 14, job_files_split: 219, refused: 0`）。随后 MCP 路径用同一 idempotency_key 重放，正常返回 `replayed: true`（幂等机制无损）。

**根因定位**（代码级）：`reconciliation._stopped()` 对查询失败的身份判"未停止"：

```python
observed = process_identity(pid)          # OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)
if observed.get("alive") is False: stopped = True
elif alive is True and both created ints: stopped = recorded.created != observed.created
else: stopped = False                    # ← alive 为 None（查询失败）即判"未证明停止"
```

`process_identity` 在 `OpenProcess` 失败且错误码 **≠ 87**（ERROR_INVALID_PARAMETER，即"进程不存在"）时返回 `alive: None`——典型如**拒绝访问**（查询目标权限更高）或 `GetProcessTimes` 在进程退出中失败。被引用的 pid 15332 是昨天 18:23 的 Creo worker：**MCP 两次拒绝时它仍存活**（今天 09:05 才随残留进程清理而死），而我的本地测试在它已死之后执行（OpenProcess 返回 87 → alive=False → stopped=True）。时间差完整解释了两条路径的分歧。

**影响**：只要作业链里存在一个"仍存活但查询进程无权/无法查询"的旧 owner（跨夜残留 worker 是常见情形），`migrate_registry`（以及依赖同一 `_stopped` 的恢复判定）就会持续拒绝，且**错误信息不说明是哪种"未证明"**。

**建议**：
1. busy 负载补上 `stop_evidence`（observed/windows_error/reason）——`reconcile_model` inspect 已有完整先例，迁移路径却没有，调用方无法自救；
2. `_stopped()` 对 `alive is None` 区分错误码：87=不存在（停止）、5=拒绝访问（**未证明**）、其他=未证明；对"拒绝访问"可结合"记录创建时间早于已验证的 Windows 启动时间"提升判定（与 BUG-074 同源规则），避免残留 worker 长期阻塞；
3. 在迁移 inspect 结果中预标注哪些条目将被 owner 守卫阻塞（现在是 apply 才撞墙）。
