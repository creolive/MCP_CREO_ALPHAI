## 0. 结论先行

**0.16.0 是 0.13.0 之后修复密度最高的一版：上一轮 4 个 P1 中的 3 个（compact 判据、长轮询、契约文案）已在 Creo 10 实测通过，`BUG-112` / `BUG-109` 也已落地；0.16.0 两个新功能 `FEAT-014 miter_cuts` 与 `FEAT-004 尺寸守卫` 在 Creo 10 上均可正常工作。**

但仍有三个结论必须如实说明：

1. **P1（新）**：`FEAT-014` 承诺的 `adjacent_bend_ends_allowed` / `miter_cuts` 元素树回显**只写进 job 目录的 `native_result.json` 与 `details/detail-aliases-*.json`，公开 `creo_get_job` 的 compact / full / `operations_result` 三种视图全部看不到**。工具描述却写着 "The element-tree echo is read back from the created feature"，黑盒调用方无法验证回显与 1e-6 容差核对是否真的发生。
2. **P1（复现）**：`creo_check_update` 的 5 秒 GitHub 网络预算在本机持续失败，`force=true` 强制重试仍失败，`latest_version` 永远为 `null`；连 `capabilities.update` 都带失败状态，黑盒用户无法确认"本地 0.16.0 是否已是最新公开版"。
3. **P0（持续核心缺口）**：`quilt_merge` 仍门禁、`loft(mode="surface")` / `boundary_blend` 仍不可提交，**任务书要求的"两个 50° 扇形截面放样 → 修剪 → 缝合 → 实体化"完整纯曲面链路在本版仍不可执行**。0.13.0 打通的只是 `fill → trim → thicken` 最小闭环。

本轮 2 个新提交的曲面作业均 `saved_file_reloaded_and_verified=true`，**未复现 0.13.0 的 `ProMdlnameBackup -1` 间歇保存失败**；但这是"没复现"，不是"已修复"的证据（见 §3.3）。

## 3. 本轮发现的问题

### 3.1 【P1 · 新】FEAT-014 的元素树回显只落盘，公开 `creo_get_job` 三种视图均不可见

**承诺**（`RELEASE_NOTES_0.16.0.md` 第 12 行）：
> 「放行时结果里记录 `adjacent_bend_ends_allowed=true`，并原样回显 `miter_cuts`（`add`、两个类型与两个数值，容差 1e-6 核对，不符合即回滚）」

**`creo_sheetmetal_flange` 工具描述**：
> "The element-tree echo is read back from the created feature"

**实测**：以 `10d1f2c0fe0c4f9a92f7a41c2c95430b`（`f_x1_miter`，`miter_cuts={width:1,offset:1}`，成功 rev 5）为例，逐视图核对：

| 视图 | 返回的 operation 记录 |
| --- | --- |
| `detail=compact` | `{op, index, label, succeeded, execution_status, effect_status}` |
| `detail=full`（整视图） | 同上 6 字段 |
| `detail=full, section=operations_result` | 同上 6 字段 |
| `detail=compact, sections=["miter_cuts"]` | **被拒**：`Unknown compact section 'miter_cuts'`，白名单里既无 `miter_cuts` 也无 `adjacent_bend_ends_allowed` |

而.job 目录内确有回执：

```
jobs/10d1f2c0fe0c…/native_result.json
  /aliases/f_x1_miter/adjacent_bend_ends_allowed = {"allowed_by_miter_cut": true, "edge_id": 266, "failure_reason": "adjacent_bend_ends", "stage": "before_create", …}
  /aliases/f_x1_miter/miter_cuts = {"add": 1, "offset_mm": 1.0, "offset_type": -4,
                                    "requested": true, "width_mm": 1.0, "width_type": -4}
```

`job.json` 的 `result` 顶层 25 个键中**没有任何** `miter` / `adjacent` 相关键（只有 `aliases_ref` 指向文件），因此 `section=result_entries`（162 条，展平自 `result`）也取不到。三份证据文件：`native_result.json`、`native_checkpoint.json`、`details/detail-aliases-dc3711b38c7dee33.json` 都含该回执，但**没有任何公开 MCP 工具能读回它**。

**附带口径不一致**：native 回执里的 `adjacent_bend_ends_allowed` 是 **dict**（含 `allowed_by_miter_cut` / `edge_id` / `ends` 等），不是发布说明写的布尔 `true`。

**影响**：
- 黑盒调用方无法判断 `PRO_E_SMT_MTR_CUTS` 是否真的被写入、宽度/偏移类型是否为 `BLIND(-4)`、1e-6 容差核对是否发生；只能看到一个 `succeeded=true`。
- 这与 0.13.0 反馈里「新算子判据 compact 不可见」是**同一类问题**：作者这次把曲面链判据补进了白名单（§2.1 已验证通过），却漏掉了 0.16.0 新功能自己的判据。
- 由于 `miter_cuts` 的切角量作者自己也标注"未量化"，回执是唯一能区分"真正写了 miter 元素树"与"只是放宽了 guard"的证据，现在这个证据对调用方不可见。

**建议**（按成本排序）：
1. 把 `miter_cuts` 与 `adjacent_bend_ends_allowed` 加入 `creo_get_job` 的 **operation result 投影**（compact 白名单 + full 的 `operations_result`），至少给出 `{add, width_mm, width_type, offset_mm, offset_type, allowed_by_miter_cut, echo_matches_request}`；
2. 或加入 compact `sections` 可选块（如 `miter_cuts`），并在 `get_job` 未知块报错的已知列表里同步；
3. 发布说明把 `adjacent_bend_ends_allowed=true` 改为与实现一致的 dict 描述，并注明回执当前仅落盘。

**可复现调用**：
```json
{"tool":"creo_get_job","params":{"job_id":"10d1f2c0fe0c4f9a92f7a41c2c95430b","detail":"full","section":"operations_result","limit":50}}
{"tool":"creo_get_job","params":{"job_id":"10d1f2c0fe0c4f9a92f7a41c2c95430b","detail":"compact","sections":["miter_cuts"]}}
```

### 3.2 【P1 · 复现】`creo_check_update` 的 5 秒网络预算持续失败，`force=true` 也无法恢复

**实测两次**（本机、同一 0.16.0 会话）：

| 调用 | `checked_at` | 结果 |
| --- | --- | --- |
| 本轮 `force=false` | `2026-11-06T13:17:25+00:00` | `status=failed`、`latest_version=null`、`from_cache=true`、`last_success_at=null`、`error="GitHub 更新检查超过 5 秒网络预算。"` |
| 本轮 `force=true`（距上次 >15 分钟，已满足提示的"15 分钟后可重试"） | `2026-11-06T13:32:30+00:00` | **同样失败**，`error` 一字不差，`latest_version=null`、`from_cache=true`、`stale=false` |

`capabilities(detail=compact).update` 原样携带这个失败对象，因此能力摘要也永远显示 `status=failed / latest_version=null`。

**影响**：
- 用户/黑盒验收**无法确认本地 0.16.0 是否等于公开最新 tag**，只能靠 `version.py` 自证；本次验收已在 §1 如实标注这一限制。
- `message` 说"15 分钟后可重试"，但到点强制重试仍失败且 `from_cache=true`，重试语义与实际行为不一致；`stale=false` 也容易让人误以为结果可信。
- 这是 0.13.0 验收时已出现过的现象，跨版本复现，不是偶发。

**建议**：
- 把 GitHub 请求超时做成可配置项（`creo_update_timeout_seconds`，默认 5 s 但允许 15–30 s），或提供 `--dir` / 本地 tag 文件的离线降级路径并在结果里明确标注 `source=offline`；
- `force=true` 应真正绕过缓存发起一次请求；失败时把 `from_cache` 与 `stale` 语义分开（缓存的失败结果应 `stale=true` 或给出 `cache_age_seconds`）；
- 结果里补 `retry_after_at` 真实时间戳，而非固定文案"15 分钟"。

### 3.3 【P2 · 持续核心缺口】完整纯曲面链路仍不可达（非 0.16.0 回归，但仍是主线阻塞）

任务书要求的路径是「两个 50° 扇形截面 **放样** → 修剪 → **缝合/合并** → 实体化」。0.16.0 现状：

| 环节 | 状态 | 依据 |
| --- | --- | --- |
| 多截面曲面放样 | ❌ `loft(mode="surface")` 提交前拒绝；无 `surface_loft` 工具；`boundary_blend` 仍不存在 | §2.3 实测；`capabilities.references.by_tool.creo_loft.surface_mode` |
| quilt 缝合/合并 | ❌ `quilt_merge` 仍 gated，`unavailable_tools=["creo_quilt_merge"]` | §2.3 实测 |
| Thin trim / `offset_mm` | ❌ 仍拒绝（作者用 2026-11-06 六方向变体说明只去带、不移动切口） | `references.by_tool.creo_surface_trim.rejected` |
| 单 quilt 修剪 → 加厚 | ✅ 可用，但只能处理**平面 fill 类**单张 quilt | `b0d7a8fb…`：800→700 mm²，1400 mm³ |
| 曲面偏置得到**可继续下游消费的新 quilt** | ⚠️ 见 §3.4 | — |

结论：**0.16.0 仍无法用纯曲面法完成五爪花瓣瓶底**，与 0.13.0 相同；本版的价值在诊断/回执/钣金与尺寸守卫，不在曲面链能力扩张。建议作者在路线图上给出 R11（真实 quilt merge 与多截面放样）的优先顺序，或明确提供"用 `revolve(angle=50)` 生成锥面片 + 逐片 thicken/boolean"的官方替代契约。

### 3.4 【P2 · 契约口径】`creo_surface_offset` 的回执与 capabilities 自述不自洽

- `families.surface_chain.limits`：「`surface_offset` returns the offset wall, **not a standalone offset quilt or a solid thickness wall**」。
- `references.by_tool.creo_surface_offset.result`：「the offset wall, measured as area times distance; it is neither a standalone offset quilt nor a solid thickness wall. `creo_thicken` / `creo_solidify` build a solid wall from a quilt, **while this operator moves the quilt along its surface normal**」。
- 实测 `f933010d…` 回执：`volume_before_mm3=0.0`、`volume_after_mm3=3999.9999999999995`、`source_area_mm2=800`、`measured_offset_distance_mm=4.999999999999999`、`target_quilt_id=82`；0.13.0 同构作业 `inspection_summary` 为 `has_solid=true`、`volume_mm3=3999.9999999999995`。

也就是说：**结果产生了 4000 mm³ 的实体体积，却同时被描述为"不是实体厚度壁"且"移动 quilt"**。调用方无法从回执判断下游还能不能拿 `target_quilt_id=82` 继续 trim / merge（回执没有新 quilt 的面积、face_count、closure 判据）。

**建议**：统一措辞并补一条明确判据，例如 `result_kind: "solid_wall" | "offset_quilt"`，若为 quilt 则给 `quilt_id / face_count / area_mm2 / closed`，若为实体则给 `body_id / volume_mm3`；并说明该结果是否允许作为后续 `surface_trim` / `quilt_merge` 的 target。

### 3.5 【未验证 · 非缺陷】BUG-113 `save_failure` / `rollback_difference` 仍缺真实失败现场

- 源码核对：`src/creo_mechdog/compact_sections.py` 把 `save_failure` / `rollback_difference` 放在 `RESULT_KEYS` 与 `PROTECTED_RESULT_KEYS`（**始终携带、不可被 `sections` 裁掉**），而不是可选块 —— 因此 §3.1 中 `sections=["miter_cuts"]` 报错列表里没有这两个名字是**设计如此，不是缺陷**，请勿误修。
- 但本轮 2 个新作业均保存成功，**未复现 0.13.0 的 `ProMdlnameBackup -1` 间歇失败**；抽查本工作区当日 6 个 0.16.0 失败作业（含 miter guard、edge 上下文、尺寸守卫），`save_failure` / `rollback_difference` 均为 `null` —— 这些是**创建前拒绝 / 再生失败**，本来就不会产出保存失败诊断。
- 回读 0.13.0 的 `a404adae…`（`ProMdlnameBackup=-1`、`rollback_status=failed`、`"Saved feature/body count changed"`）经 0.16.0 `get_job(compact)` 仍只有旧字段，没有新诊断 —— 因为它们是**执行期由 executor 写入**的，不会追溯补进旧 job，属预期行为。
