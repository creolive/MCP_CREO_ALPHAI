## 3. P-A【严重】坐标标注对「直线+圆弧」混合轮廓过度约束

### 3.1 现象

P05 首张草图 `S05-01`（履带环带外轮廓，5 条直线 + 4 段圆弧，闭环）提交：

```
[coordinates] job=b2b25f44 status=failed stage=execute_sketch
  msg=Coordinate dimensioning changed the supplied geometry; maximum deviation mm=53.042605
[auto]        job=cf058299 status=failed stage=execute_sketch
  msg=Coordinate dimensioning changed the supplied geometry; maximum deviation mm=117.597000
[first2]      job=f62b8c51 status=failed stage=execute_sketch
  msg=Coordinate dimensioning changed the supplied geometry; maximum deviation mm=53.042605
```

`native/sketch_coordinates.cpp` 的 `verify_coordinate_plan()` 在 `tolerance_mm=1e-5` 下记录：

```
GEOMETRY_STAGE_SHAPE points=14 translation=5.375103884207 shape=53.042604872751 rigid=0 total=9
COORDINATE_DEVIATION entity=l001 point=start axis=0 moved=10.554693867876
COORDINATE_DEVIATION entity=l001 point=start axis=1 moved=0.949593826061
COORDINATE_DEVIATION entity=l003 point=end   axis=0 moved=9.621976450138
COORDINATE_DEVIATION entity=l003 point=end   axis=1 moved=51.789167952192
COORDINATE_DEVIATION entity=l005 point=start axis=0 moved=0.571487951799
COORDINATE_DEVIATION entity=l005 point=end   axis=1 moved=12.522992240816
COORDINATE_DEVIATION entity=l007 point=end   axis=0 moved=15.377745027240
COORDINATE_DEVIATION entity=l008 point=start axis=0 moved=15.377745027240
COORDINATE_SHARED_VERTEX_SKIPPED=coord_l008_start
SKETCH_SHIFT_DEFORMED max=52.675424516442 residual=48.781052779232
BUILD_FAILED=Coordinate dimensioning changed the supplied geometry; maximum deviation mm=53.042605
```

**注意**：输入草图本身是严格闭合且圆弧端点精确落在相邻直线端点上的（`OPERATION_INDEX=0 INPUT` 已核对，例如 `a002` 圆心 (114.483237918797, -86.25156829155736)、R88.504，其起止角反算端点与 `l001`/`l003` 端点一致）。形变是**求解之后**才出现的，不是输入几何不合格。

### 3.2 机理（供作者定位）

`coordinate_dimensions()` 对每类实体加的尺寸：

* 每条 `line`：2 个端点 × 2 轴 = 4 个尺寸（共享顶点只跳过一次）；
* 每段 `arc`：圆心 2 个 + 半径 1 个 + 两个极角 `PRO_TK_DIM_ANG_POLAR` = 5 个尺寸，**圆弧端点不直接标注尺寸**；
* 圆弧端点与直线端点由 Creo 的隐式重合约束绑定。

以 P05 S05-01 为例：9 个实体理论自由度约 40，闭环重合约束约 −18，剩余约 22；而实际创建的尺寸约为
`8 条线 × 4 − 1 个共享点 × 2 + 4 段圆弧 × 5 = 50` 个，**远超自由度**。
求解器为满足这组互相冲突的尺寸只能改形（`SKETCH_SHIFT_DEFORMED`），随后 `verify_coordinate_plan()` 又用 1e-5 mm 保真门把「自己改坏的结果」判失败。
这解释了为什么含圆弧+直线交替的草图必挂，而纯直线/矩形/圆/折线草图（本轮 P03/P04/P07…P31 多数）能顺利通过 `coordinates`。

### 3.3 影响面

| 零件 | coordinates 失败 | 最大偏差 |
|---|---|---|
| P05 履带板 | `b2b25f44` | 53.042605 mm |
| P02 负重轮盘 | `886cc3fa` | 0.104757 mm |
| P01 齿轮盘 | `16c6eda9` | 0.003509 mm |

### 3.4 建议

1. 在 `coordinate_dimensions()` 里**识别闭环拓扑**：圆弧端点与直线端点重合时，不要同时给「直线的端点坐标尺寸」和「圆弧的圆心+半径+双极角尺寸」；二选一，或把圆弧端点也纳入 `placed` 共享顶点表并相应减少尺寸。
2. 或者在求解前按自由度预检尺寸数，超约束时明确报 `over_constrained_coordinate_dimensions` 并附带 DOF/尺寸计数，而不是让求解器改形后再报一个 53 mm 的「geometry changed」。
3. 提供 `dimensioning="none"/"raw"` 之类的入口：把用户给的坐标原样写入 section 并跳过自动标注，供「点列即最终几何」的逆向重建场景使用。

## 4. P-B【严重】autodim 求解失败仍判成功

P05 改用 `dimensioning="autodim"` 后**作业成功**：

```
[autodim] job=0b81dd8b status=succeeded stage=verified model=0c8da2cd ops=18
  msg=General feature plan completed
```

但同一作业的 `native.log` 中 9 张草图全部求解失败、且形变量巨大：

```
SKETCH_SOLVE=-1 mode=autodim                     (×9)
GEOMETRY_STAGE_SHAPE points=14 shape=12.619616281217 rigid=0
GEOMETRY_STAGE_SHAPE points=16 shape=58.962589107997 rigid=0
GEOMETRY_STAGE_SHAPE points=84 shape=0.124756452128 rigid=0
GEOMETRY_STAGE_SHAPE points=40 shape=2.758177141899 rigid=0
...
```

`schema.py` 注释写明 autodim 的 1e-3 mm 保真门是「只告警不失败」，因此**形变量被降级为 warning**，`SKETCH_SOLVE=-1` 也未作为失败条件。
读回的几何与 TXT 标称对比：

| 项 | TXT | autodim 实测 | 偏差 |
|---|---|---|---|
| 包围盒 X | −1046.469 … 503.585 | −1046.0095 … 500.7451 | Xmax −2.840 mm |
| 包围盒 Y | −210.077 … 304.264 | −210.1125 … 304.3355 | ≤0.072 mm |
| 包围盒 Z | 0 … 275 | 0 … 275 | 0 |
| 体积 | 23116.7 cm³ | 27910.926 cm³ | +20.7% |

> 体积偏大还包含「8 张面上草图未建」的因素，不能全部归因于 autodim；但包围盒偏差与 `shape=58.96 mm` 已经足以说明该 success 回执不代表几何保真。

**建议**：`SKETCH_SOLVE != 0` 应当直接判作业失败（或至少在 `result` 顶层给出 `sketch_solve_failures[]` 与 `max_shape_deviation_mm`，并把 `stage=verified` 降级为 `verified_with_warnings`），避免调用方把带病模型当作成功成果。

## 5. P-C `auto` 静默回落、错误信息缺上下文

`native/sketch_coordinates.cpp::profile_dimensioning()`：

```cpp
std::string requested = op.value("dimensioning", "auto");
if (requested != "auto") return requested;
...
return count >= 10 || extent > 1000 ? "coordinates" : "autodim";
```

用户提交 `auto` 时无法从回执看出被改成了 `coordinates`；P05 的 `[auto]` 与 `[coordinates]` 报同一句
`Coordinate dimensioning changed the supplied geometry`，排查时容易误判为「两个模式都坏了」。
另外 P02 的 autodim 失败信息为 `Toolkit call AutodimensionSketch failed with code -1 during execute_sketch`，
没有草图名、实体数、是否超约束等上下文。

**建议**：在 job result / 草图操作记录里明确写出 `requested_dimensioning` / `effective_dimensioning` / `downgrade_reason`，并让失败信息带上 label 与实体统计。

## 6. P-D 纯 3D 框架的斜面草图没有直接入口

TXT 里 10 张「模型面（面上草图）」把框架写全了，例如：

```
S05-03｜模型面（面上草图）；草图原点 O=(17.525, 185.862, 0) mm；
        u 轴 (0.995584, -0.093875, 0)；v 轴 -Z；法线 n=(0.093875, 0.995584, 0)
```

0.16.0 的 `validate_sketch_plane_frame()` 强制 `plane.reference` 必须是 `{kind:...}` 的 live/datum 选择，
`native/generic.cpp` 的 explicit plane 分支也只从 `reference` 取法向。因此**给了 O/u/v/n 也不能直接建平面**，
必须按 `docs/validation/WORKBUDDY-0.11.1.md` 的序列额外提交 3 个 `datum_points` + 1 个 `datum_plane(through_points)`，
再用 `plane={type:"frame", origin, reference:{kind:"datum_feature",label}, u_axis}`。
本轮据此为 P05/P27 生成了完整变体（`parsed/plans_faces/`，P05 66 ops、P27 22 ops），每个面步多 4 个纯辅助 operation。

**补充实测**：即便按官方序列造出 frame 平面，frame 草图用 `dimensioning="coordinates"` 仍会求解失败：

```
OPERATION_INDEX=8 INPUT={"label":"s03", ..., "dimensioning":"coordinates", ...}
SKETCH_SOLVE=-1 mode=coordinates
SKETCH_SOLVE_WITHOUT_INFERENCE=-1
AutodimensionSketch=-1
BUILD_FAILED=-1
job=a8ce8f98 status=failed stage=execute_sketch
  msg=Toolkit call AutodimensionSketch failed with code -1 during execute_sketch
```

推测与 `pin_coordinate_origin()` 依赖「投影出来的基准线 anchors」有关：纯 frame 平面没有可用的 axis-aligned 投影线，坐标系原点无法被钉住。建议在 frame 平面分支里用显式 `origin` 直接锚定 2D 坐标系，而不是复用 named datum plane 的 anchor 逻辑。

同类限制：`round` 的 `references` 要求 live edge id，TXT 只给了 2/8/12 个「边锚点坐标」，无法直接提交，6 个圆角步骤未能重建。

**建议**：允许 `plane.reference` 使用 `{"kind":"frame","origin":[...],"u_axis":[...],"normal":[...]}` 一步建面；
`round` 支持按 3D 边锚点坐标解析 edge（或提供 `edge_by_point` 选择器）。这会让「自然语言/点列 → 参数化特征树」的重建路径少一层不必要的 live-id 依赖。

## 7. P-E 通用重生失败信息缺少 Creo 原始错误

P10 `e03`（S10-03，沿 −Z 深 887.2）在 3 个变体下均失败：

```
stage=execute_extrude  message=Regeneration produced a failed, suppressed or incomplete feature
failed_operation = {feature_label:"e03", index:5, sketch_name:"s03",
                    pro_error:null, pro_error_source:"unsupported", toolkit_call:null}
```

`pro_error_source="unsupported"` 意味着拿不到 Creo 原生错误码。TXT 12.3 提示共面接触加料会产生独立实体；
本轮按 12.3 的 0.001 mm 外扩口径做了 `overlap` 变体后验证。建议把 `ProFeatureStatusGet` / 重生错误码与失败特征 id 投影到 `failed_operation`。

## 7b. P-F 大草图坐标标注的性能与作业生命周期

* 性能：为绕开 §3 的超约束，把 P05 的 8 段 TXT 圆弧展开成 540 条弦段（矢高 ≤0.01 mm）后，
  `native.log` 中出现 **1349 次 `ProSecdimCreate`**，该作业 600 s 内只推进到 16/18 个 operation。
  即坐标标注的开销随实体数近似线性且常数很大，对「点列级」重建不友好。
  建议对 lines-only 闭合轮廓提供批量/免标注入口，或给出 `max_dimensions` 之类的保护。
* 生命周期（**集成侧风险，非内核缺陷**）：本轮用 Python stdio 客户端托管 `server.py`，
  客户端在 `wait(timeout=600)` 到点后退出，server 与其 native runner 一并被终止，
  `jobs/20513554…/job.json` 永久停在 `status=running`（`native.log` 停在 `OPERATION_INDEX=15`）。
  随后的提交全部被 `toolkit_busy` 拒绝，直到 `bridge.py::admission_holder()` 通过
  `_pid_alive(runner_pid)` 判定 claim 失效并自动清除——这一自动清理**工作正常**，值得肯定。
  建议让 `creo_execute_plan` 的作业在客户端断开后仍可跑完（或至少把 job 标成 `abandoned`），
  避免「客户端超时 → 长作业被杀 → job 永久 running」的组合。

## 8. 本轮采用的规避方式（供作者复现）

| 变体 | 做法 | 依据 |
|---|---|---|
| `autodim` | 全部草图显式 `dimensioning="autodim"`，绕过 `auto`→`coordinates` 回落 | 见 §5 |

## 9. 验证边界与未做项（诚实降级）

* 本文所有「成功」仅指 MCP 作业回执 `status=succeeded / stage=verified`；**不等于几何与 TXT 完全一致**。
  autodim 类作业存在 §4 的形变，已在最终交付报告中逐件标注。
* **本轮最终采用**：P05 改用 `chords`（TXT 圆弧按矢高 ≤0.01 mm 展开成弦段后 `coordinates` 标注，18 ops 成功），
  实测包围盒除 Xmax +0.067 mm 外与 TXT 完全一致，D.7 的 I069/I070 从 2.8399 mm 偏差收敛到 0.0674 mm PASS；
  P10 改用 `overlap05`（TXT 12.3 允许的共面 0.5 mm 内扩），9 步全部建成；
  P02 用 `chords_prefix10` 建到步05；P01 沿用 `autodim`（体积 467.6 cm³ 与 TXT 相符）。
* 6 个圆角步骤（P03×2 / P12×3 / P26×1）因需要 live edge id 未重建；10 张面上草图在
  `plans_faces` / `chords_faces` 变体中均于 frame 草图处 `AutodimensionSketch=-1` 失败，故未进入最终模型。
* TXT 12.6 自认 P02 步09…步12 的框架与点列矛盾、实建必失败，本轮不把它们算作 MCP 缺陷；
  TXT 4.3 自认 P10 实测包络与动作推导包络相差 5.00 mm，因此 D.7 的 I022 差 5.000 mm 也不算 MCP 缺陷。
* 本轮未调用任何其他 CAD MCP，未导入任何实体，未引用工作空间外的模型文件。
* 最终成果与完整实测表见 `TXT-only重建结果报告_CREO_0.16.0.md`。
