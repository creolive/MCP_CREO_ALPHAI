## 报告现象（外部环境已证实）

升级 0.3.5 后首次 `creo_reconcile_model` apply（**省略** `expected_pending_job_id`，参数合法）：

1. 作业返回 `unknown_outcome` / `stage: reconciliation_unconfirmed`，消息 `Recovery refused: Creo session changed since recorded evidence`。
2. 该作业已是终态（有 `finished_at`），但模型 `recovery_pending` 仍保留其 id；下一次成功 apply 后才被覆盖（外部第二次 apply 成功）。

## 问题定性（待本机核实）

1. **语义矛盾**：作业在执行前被明确拒绝（"refused"，会话变更/证据过期），结果却是 `unknown_outcome`（不确定是否执行）。"未执行"在此是确定的，应记为确定性失败（如 `refused` / `failed` 附 reason），`unknown_outcome` 仅保留给"原生进程可能已开工"的情形。
2. **`recovery_pending` 悬挂**：终态拒绝作业的 id 仍挂在模型上，期间 inspect 会把它列为 owner，增加混淆。

需先核对：该分支在服务侧是否确实发生在任何原生调用之前；若是，按确定性失败处理并立即清除 `recovery_pending`；若存在原生已开工的可能（如锁内阶段才判定会话变更），则当前标注有依据，改为在返回中说明判定阶段。

**本机先例**：[BUG-055](BUG-055.md) 卡 2026-10-17 M2 收尾补录中，本机跨会话保护拒绝同样返回作业 `unknown_outcome`（消息同款 "Creo session changed since recorded evidence"），当时重点验证模型未被改动、未审视终态标注语义。即该分支在本机与外部 Creo 9 均可观察，非外部独有。

## 范围

- 限于 `creo_reconcile_model` 的执行前拒绝分支（会话变更/证据过期）终态标注与 `recovery_pending` 生命周期。
- 不改变 inspect→apply 凭证协议、四动作语义与 BUG-055 已闭环的空值契约；不影响真正 unknown（原生进程中断）作业的保护语义。

### 2026-10-18 DEV-040 离线实施

已区分两条路径，原报告“执行前”假设不能整体成立：

- 原生消息 `Creo session changed since recorded evidence` 产生于 connect_creo 成功、记录会话指纹之后。因此本轮不改为确定性失败，也不清其 recovery_pending；增加 `failure_phase=native_worker_started`、reason 和保守派发说明，保留原始消息与 failed_stage。该字段表示原生可能开工，不保证已实际创建进程。
- 纯 Python 准入后、原生派发前的会话选择/部署/证据等变化，离线复现为 failed 但 recovery_pending 悬挂。已修为 `reconciliation_refused` / `before_native` 并给稳定 reason，在通道锁内仅清本恢复作业自己的占位；runner 启动失败同样处理。原 pending_job、unknown 状态、revision 和审计不变。清理失败、无法取得通道锁、原生中断与原生后的同款检查失败均保留相应保护。

600 秒 TTL 仍在准入时校验；准入前过期直接拒绝，不创建 job 或新占位。未新增执行期 TTL、自动续期或重试。compact/full 与幂等重放同步阶段和清理字段；BUG-055 空值契约保持。

开发者离线及真实 stdio 夹具回归见 [DEV-040 记录](../validation/DEV-040-offline-2026-10-18.md)，原生结果以合成替代明确隔离；[WorkBuddy 提示词](../validation/DEV-040-WorkBuddy-test.md)已准备但未执行。当前连接限制保留，未验证真实会话切换/中断和外部 Creo 9 路径，不关闭本卡。
