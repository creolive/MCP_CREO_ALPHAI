# DEV-045：Release body 固化两包 SHA256 检查

类型：工程整理

优先级：P2

状态：验收中（2026-10-21 RELEASING 清单与记录模板已固化；下次发布实际执行核对）

目标版本：待定

来源与关联：[0.4.4/Creo 10 反馈](../validation/feedback-0.4.4-2026-10-21/report-dev027-030.md) §4.1 与 §5.1（"0.4.1/0.4.2 直接写在 Release body（我建议过并获采纳），0.4.3 也在 body，0.4.4 的 body 没写……建议固定为 Release body 必含两包 SHA256"）。

## 问题或目标

附件校验和的呈现方式在版本间漂移：0.4.1～0.4.3 的 Release body 直接列出源码包/种子包文件名及完整 SHA256，0.4.4 漏写（只能去 main 分支 `docs/validation/RELEASE-0.4.4.md` 取），下游升级者被迫多走一步且无稳定预期。

## 范围

本次包含：

- `docs/development/RELEASING.md` 发布清单固化：Release body 必须直接列出源码包、种子包的文件名及完整 SHA256，并随发布核对流程核对远端附件与 body 一致。
- 发布历史与已发布附件保持原样，不回填旧 Release。

不包含：自动化发布脚本改造（现有手动流程上增加检查项即可）；旧 Release 补写。

## 验收标准

| 环境 / 用例 | 命令或操作 | 可判断的预期结果 |
| --- | --- | --- |
| 文档 | RELEASING.md 评审 | 清单明确包含"Release body 两包文件名+SHA256"及远端核对步骤，与既有版本发布规则无冲突 |
| 下次发布 | 按清单执行 | Release body 含两包 SHA256 且与远端附件哈希一致 |

## 实现与证据

2026-10-21 实施（分支 `codex/bug077-registry-split`）：`docs/development/RELEASING.md` 发布门槛新增第 7 项——Release body 必须直接列出源码包与种子包文件名及完整 SHA256，发布后核对远端附件哈希与 body 记载一致再报告交付完成，并说明已发布 Release 与附件保持原样不回填；发布回归记录模板同步标注（文件名与完整哈希写入 body、远端逐项核对）。
