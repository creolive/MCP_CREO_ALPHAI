# DEV-045：Release body 固化两包 SHA256 检查

类型：工程整理

优先级：P2

状态：已完成（外部确认关闭，2026-10-23 按 0.5.0 外部报告三 §4 关闭并移入完成档案）

目标版本：未排期

来源与关联：[0.4.4/Creo 10 反馈](../validation/feedback-0.4.4-2026-10-21/report-dev027-030.md) §4.1 与 §5.1（"0.4.1/0.4.2 直接写在 Release body（我建议过并获采纳），0.4.3 也在 body，0.4.4 的 body 没写……建议固定为 Release body 必含两包 SHA256"）。

## 问题或目标

附件校验和的呈现方式在版本间漂移：0.4.1～0.4.3 的 Release body 直接列出源码包/种子包文件名及完整 SHA256，0.4.4 漏写（只能去 main 分支 `docs/validation/RELEASE-0.4.4.md` 取），下游升级者被迫多走一步且无稳定预期。

## 范围

本次包含：

- `docs/development/RELEASING.md` 发布清单固化：Release body 必须直接列出源码包、种子包的文件名及完整 SHA256，并随发布核对流程核对远端附件与 body 一致。
- 发布历史与已发布附件保持原样，不回填旧 Release。

不包含：自动化发布脚本改造（现有手动流程上增加检查项即可）；旧 Release 补写。

## 验收标准

| 环境 / 用例 | 命令或操作 | 可判断的预期结果 |
| --- | --- | --- |
| 文档 | RELEASING.md 评审 | 清单明确包含"Release body 两包文件名+SHA256"及远端核对步骤，与既有版本发布规则无冲突 |
| 下次发布 | 按清单执行 | Release body 含两包 SHA256 且与远端附件哈希一致 |

## 实现与证据

2026-10-21 实施（分支 `codex/bug077-registry-split`）：`docs/development/RELEASING.md` 发布门槛新增第 7 项——Release body 必须直接列出源码包与种子包文件名及完整 SHA256，发布后核对远端附件哈希与 body 记载一致再报告交付完成，并说明已发布 Release 与附件保持原样不回填；发布回归记录模板同步标注（文件名与完整哈希写入 body、远端逐项核对）。

下次发布（随 BUG-077/FEAT-047 的交付）实际执行时按本条核对；本条自身为文档改动，不单独触发发布。

## 2026-11-04 C01：sidecar 上传缺口与远端核对

来源：[0.11.7 反馈映射](../validation/feedback-0.11.7-2026-11-04/MAPPING.md) F02，以及 0.12.0 发布后的同一现象。复核结论与 0.11.7 反馈一致：`tools/package.py`、`tools/package_seeds.py` 一直生成 `<zip>.sha256`，缺口在**上传清单与远端核对**——两版发布命令都只列出两个 ZIP，`RELEASING.md` 第 7 条也只要求把哈希写进 Release body，未把 sidecar 列为附件门槛。

本次处理（开发分支，未合 main、未发布）：

- `docs/development/RELEASING.md`：第 5 条说明 sidecar 是发布附件而非本地临时产物；第 7 条把附件固定为四个文件，要求上传命令逐个列出、禁止 `*.zip` 通配，并给出远端核对方式；回归记录模板增加附件清单与四个附件核对行。
- `docs/PUBLISH_GITHUB.md`：新增"发布附件（所有新版本固定四个）"一节，0.2.5 的文件名降为历史示例。
- `tools/package.py`、`tools/package_seeds.py`：成功输出打印 sidecar 路径与四附件上传清单，种子 sidecar 缺失时告警。
- 新增 `tools/check_release_assets.py`：下载指定 tag 的附件并核对恰有四个文件、两个 sidecar 的哈希与对应 ZIP 摘要一致；新增 `tests/unit/test_release_assets.py` 10 项回归（齐全、缺 sidecar、哈希不符、目标名不符、多余附件、多行 sidecar、CLI 退出码）。

远端处理（2026-11-04，用户明确授权"仅补 v0.12.0"作为"不回填旧版本"规则的例外）：

- 补传前 `--tag v0.12.0` 与 `--tag v0.11.7` 均报缺各自两个 `.zip.sha256`（exit 1）。
- `v0.12.0` 已补传两个 sidecar：先按远端附件实际字节核算（源码包 `f18f543748a8e442d67c20e7002f9a1f2e3a09757f44d43ef437291b4b8288d5`、种子包 `4385fa21bb49a42620479f89b8c51b94946c02d0f6e79281cab360807d339865`，与发布记录及 GitHub 资产摘要一致），再以 `gh release upload` 新增（未替换任何 ZIP）。补传后 `tools/check_release_assets.py --tag v0.12.0` 通过：四个附件齐全、两个 sidecar 与对应 ZIP 摘要一致（exit 0）。
- `v0.11.7` 按用户决定保持原样，不补传；该版缺 sidecar 的事实保留在本记录与反馈映射中。
- `docs/validation/RELEASE-0.12.0.md` 位于 `main`，其中的附件表仍只列两个 ZIP；补传事实需在该记录随下一次 `main` 提交回填，本分支不复制 `main` 文件。
