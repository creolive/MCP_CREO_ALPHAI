# BUG-076：收养链路 16 MiB 元数据预算阻断真实模型（定位诊断）

类型：缺陷

优先级：P1

状态：验收中（0.4.5 定位诊断与 2026-10-21 资料分离精修均已实施；原环境根因证据已取得——阻断修复移交 BUG-077，本卡剩余为实机链路与 WorkBuddy 复核）

目标版本：0.4.6

来源与关联：[0.4.2/Creo 10 反馈](../validation/feedback-0.4.2-creo10-2026-10-21/report.md) §4.1（P0'）；[处理计划](../development/CREO10-0.4.2-FEEDBACK-PLAN-2026-10-21.md) 首批第 1 项；关联 FEAT-006/008（收养错误信息与预检诊断，同批实施）。

分类依据：外部环境现象已证实（两个模型均报错），命中哪一类 16 MiB 读取未定；首批交付可定位的诊断，不以诊断完成代表阻断已修复。

## 问题或目标

已证实现象（外部 Creo 10 / 0.4.2，2026-10-20）：当前窗口为外部装配 HYD_CYLINDER_ASM 与刚用 `creo_open_file` 打开的 1,054,728 字节真实零件 MX_UP（mx_up.prt.7）时，`creo_adopt_current_model(mode=inspect)` 均报 `Adoption metadata exceeds the 16 MiB read budget`，收养链路对真实模型不可用。

待验证根因：`src/creo_mechdog/adoption.py` 的 `_read()` 对超过 16 MiB 的文件抛裸 `ValueError`，该读取同时服务于四类元数据——原生结果（native_result.json）、历史模型登记（model.json）、证据令牌（evidence-*.json）、提交日志（job.json/预检 job）。报告现象无法确定命中哪一类；1 MB 零件直接产生 16 MiB inspection 结果的可能性未经证实。反馈中"类型门控发生在重量级收集之后"的根因判断经 2026-10-20 代码核对未采纳：原生收养入口已在完整 inspection 前拒绝装配（unsupported_model_type 前缀）。

预期行为：预算超限返回稳定原因码 `ADOPTION_METADATA_BUDGET_EXCEEDED`，携带 `metadata_kind`（四类之一）、服务内相对路径、`actual_bytes`、`budget_bytes`、`failed_stage`、已有 job/model 标识及恢复指引；同步工具错误返回一致的 JSON 文本与结构化内容，后台失败保留在任务结果中。取得超限文件类别、实际字节数、预检 job_id、受测部署身份及原始原生结果后，再形成对应读取路径的精修方案。

## 范围

本次包含：

- `_read()` 预算错误结构化（稳定原因码 + 六要素 + 恢复指引），覆盖上述四类读取调用点。
- 四类超限隔离用例（构造超限文件，不需要 Creo），确认调用阶段、失败收尾与保护状态；边界大小（恰 16 MiB / 16 MiB+1 字节）。
- 收养失败保留长度受控的 `native_log_tail`；错误收尾读取超限时不得覆盖原始诊断（原始错误优先，二次超限作为附注）。
- 已派发或已提交任务的保护保留：预算错误不重放 native、不清保护、不重复执行。

不包含：全量证据存储重构、统一提高限额、跳过历史登记或删减几何核验来消除报错；证据收集分节化（进入后续精修方案，视定位结果另定）；会话擦除工具（另期）。

## 2026-10-21 第二批范围：资料分离精修

按[0.4.3 反馈完善计划](../development/0.4.3-feedback-improvement-plan-2026-10-21.md) P1，在 0.4.5 诊断基础上消除预算阻断本身：

- 控制元数据与完整检查资料分离：结果、令牌、请求和登记使用摘要及受控文件引用，完整几何不再反复内联；原生完整基线文件保留。
- 完整资料绑定所属目录、SHA256、会话和令牌；保留源模型、复制后、保存重载后的带容差比较（verify_recovery 语义不变）。
- 覆盖 inspect/apply/prepare/confirm、快照续签及登记读取（含 reconciliation 的登记读取路径），避免只修预检、后续再次超限。
- 兼容旧内联记录（读取路径回退内联键），公开调用参数保持不变；引用篡改、缺失、过期准确拒绝，无半登记。
- 不统一提高限额、不跳过历史登记、不删减几何核验。
