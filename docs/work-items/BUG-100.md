# BUG-100：背靠背提交在 runner 取得通道前被接受并排队

日期：2026-11-02。类型：缺陷。优先级：P2。状态：已修复（0.11.1 候选；离线单测通过，背靠背实机复验待下个会话）。目标版本：0.11.1。关联 BUG-009（并发现状，不重开）、DEV-053 Q04。

## 现象

两个 `creo_execute_plan` 背靠背提交（间隔约 50 ms，第一次尚未进入原生执行）时：

- 第一次返回 `status=queued`，随后正常执行；
- 第二次 **不是** `status=busy`，而是同样被接受，返回 `status=queued`，其 runner 在锁上等待，第一次结束后再执行。

但服务对外声明的是即时拒绝、不排队：

- `creo_capabilities` 的 `scheduling.admission = "reject_busy_without_creating_a_job"`；
- `AGENTS.md`：通道忙碌时立即拒绝（`isError=true`、`status="busy"`），不排队、不自动重试；
- BUG-009 关闭时也按“保持即时拒绝策略，不增加通用排队能力”记录。

通道确实被占用时行为正确：等第一次作业进入 `executing_feature_plan` 后再提交，第二次得到完整 busy 回执（`blocking_job_id` 指向第一次作业、`blocking_operation`、`accepted=false`、未新建 job 目录），见同一份证据文件里的 busy 段。

## 机理

- `generic_bridge.submit` 只在提交登记阶段拿 `toolkit_lock(wait_seconds=0)`（`generic_bridge.py:198`），拿不到才返回 busy；
- 真正执行由独立 runner 进程异步完成，runner 以 `wait_seconds=120` 等锁（`generic_bridge.py:476`）；
- 从“接受并落 job 目录”到“runner 真正拿到锁”之间存在空窗，空窗内的第二次提交能通过准入并被排队。

## 影响与未验证

- “无队列”不再是可断言的契约：可同时存在两个已接受作业，串行执行。
- 同一模型的 revision 只在提交时校验（`generic_bridge.py:238`），第二个作业若在空窗内以旧 `expected_revision` 被接受，可能在第一个作业推进 revision 之后仍然执行，属于潜在丢失更新。本轮只用两个**不同新模型**复现，同模型旧 revision 窗口**未验证**（未做该实验，避免在用户会话写错模型）。
- 未验证：>2 个并发提交、runner 启动更慢时的窗口大小、busy 与 queued 的边界是否在文档中另有定义。

## 验收标准

| 场景 | 预期 |
| --- | --- |
| 任意时刻已有“已接受但未开始”的作业，再提交 | 要么立即 busy（与声明一致），要么文档把“有界排队”写成明确契约（容量、顺序、等待预算、revision 复核） |
| 同一模型空窗内两次提交 | 第二次必须被拒绝，或在锁内重新校验 revision 并拒绝陈旧写；不得出现丢失更新 |
| 真实并发（第一次已在执行） | 保持现状 busy 语义与 5 字段回执 |

## 证据

`build/live-0.11.1/q04_admission_race.json`（SHA256 `7821D328DE66BA605229944D1B123A9C8E32CFC5FBEBAE8A9402D897C915F19A`）：`first.status=queued`、`second.status=queued`、`second.code=null`；同文件 `q04_stage_busy.json` 是通道已占用时的正确 busy 回执。

## 实现与证据（2026-11-02 离线修复）

按验收标准第一列选择"立即 busy"路线，不引入队列、不改变既有 busy 回执形态：

- **通道预约**：`bridge.py` 新增 `toolkit-channel.json` 预约原语（`channel_claim` / `admission_holder` / `write_channel_claim` / `clear_channel_claim` / `_pid_alive`）。预约从"作业被接受"贯穿到"runner 收尾"。
- **两条提交路径同一准入规则**：`generic_bridge.submit`（execute_plan）在校验完、落任何状态前，`bridge.create_job`（create_plate）在锁内第一步，先 `admission_holder()` 判定：存在"已接受未终态"的预约即抛 `ToolkitBusy`（holder 携带 job_id/model_id/operation，回执复用既有 5 字段 busy 形态）。预约在 runner 子进程 Popen 之后、仍持有提交锁时写入（含 runner pid）。
- **runner 释放**：`bridge.run_job` 以 try/finally 包裹分发，无论终态如何都释放本作业的预约（只清仍指向本作业的预约）。
- **过期与保守规则**：预约指向的作业已到终态（status 不在 queued/running）或 runner 进程可证死亡（OpenProcess/GetExitCodeProcess 判定）时，下一次准入自动清预约放行；runner pid 缺失/不可判定/拒绝访问一律视为占用（不凭缺失证据释放通道）。作业本身的状态不动：runner 死亡的 queued 作业保持原样待检查，其模型仍由 `pending_job` 守卫。
- **同模型语义不变**：同模型空窗内重交仍先命中 `pending_job` 守卫（回执 `blocking_operation=pending_job`），不受影响；跨模型/新模型空窗现在按契约拒绝。
- **次生关闭**：卡片"影响"里记录的同模型空窗陈旧 `expected_revision` 被接受再执行的丢失更新窗口，随空窗拒绝一并关闭。

单测（`tests/unit/test_toolkit_channel.py` 新增 6 例：背靠背新模型拒、跨既有模型拒、死 runner 预约过期放行、终态预约过期放行、plate 与 generic 共享同一预约、通道等待超时释放预约；5 个载荷对比测试文件按"runner 收尾后释放"语义适配，准入逻辑保持真实覆盖）：该文件 22/22、全量 2096 项 0 failures，`tools/dev_check.py` success=true（变更文件全部过 ruff format）。

**待实机复验**（下个会话）：真实背靠背双提交第二个应得 busy（`blocking_job_id` 指向第一个）；真实并发 busy 语义与回执不变。
